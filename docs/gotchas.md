## Database & Migrations

- **`prisma migrate deploy` does NOT actually run on this DB**: As of 2026-04-26, the production Postgres instance has no `_prisma_migrations` table — meaning Prisma's migration runner has never successfully applied any of the files in `prisma/migrations/`. Every column in production was created by raw `ALTER TABLE IF NOT EXISTS` statements in `src/app/api/migrations/run/route.ts`. **When adding a new schema field, you MUST also add a matching `ALTER TABLE` to that route AND have someone POST to `/api/migrations/run` after deploy. Adding a `prisma/migrations/<name>/migration.sql` file alone is a no-op.** Symptoms when you forget: admin dashboard shows "Something went wrong / An unexpected error occurred in the admin dashboard" and the customer portal shows zero projects, because Prisma's `include: { ... }` generates SELECTs against columns that don't exist. Permanent fix is to retrofit `_prisma_migrations` (mark every existing migration as applied via `prisma migrate resolve --applied`) so future migration files actually run; until that's done, the raw-SQL route is the source of truth.
- **Every Prisma schema field MUST have a migration**: Never add a field to `schema.prisma` without a corresponding migration SQL. Without a migration, any Prisma query without an explicit `select` will crash with "column does not exist". Runtime `ALTER TABLE` hacks in API routes are not sufficient — they only run when that specific endpoint is called, not when other pages query the same model. The migration `20260310000000_add_missing_columns` fixed a batch of these.
- **Prisma schema + raw SQL migration must stay in sync**: Any column added via raw SQL migration must also be added to `prisma/schema.prisma`. Otherwise Prisma will throw `column (not available) does not exist` on any query touching that table. When adding schema fields, also check for `select` clauses in server components that pass data to components typed as the full Prisma model — those selects need the new fields too.
- **Production migrations must use API endpoints, not Prisma CLI.** Never run `prisma migrate` directly on production.
- **Reporting tables are NOT Prisma-managed**: The reporting system uses raw SQL tables (`report_tickets`, `report_time_entries`, `report_ticket_notes`, `report_aggregations`, `report_schedules`, `report_targets`) created via migration endpoint. `src/lib/reporting/ensure-tables.ts` auto-creates them if missing. Don't try to add these to Prisma schema.
- **SOC tables are NOT Prisma-managed**: SOC uses raw SQL tables (`soc_incidents`, `soc_activities`, `soc_config`, `soc_rules`, `soc_known_benign`) created via `/api/soc/bootstrap` or `/api/soc/migrate`. Same pattern as reporting.
- **HR routes use raw pg, NEVER Prisma**: All routes under `src/app/api/hr/` use `getPool()` from `src/lib/db-pool.ts`. Do not switch them to Prisma — it caused 500s. Always pass `companySlug` in the request body (POST) or query params (GET).
- **HR Prisma models use `@map()` to point at snake_case columns**: HR routes use raw pg (above) and the live DB has snake_case columns (`company_id`, `submitted_by_email`, etc.). The `HrRequest`, `HrRequestStep`, and `HrAuditLog` models in `schema.prisma` declare camelCase field names with explicit `@map()` directives so Prisma reads the same columns the raw pg routes write to. Do not strip those `@map()` directives or any future Prisma query against those models will look for columns that don't exist.
- **Prisma column names are camelCase** — raw SQL must use quoted camelCase (`"companyId"`, `"displayName"`, `"autotaskCompanyId"`), NOT snake_case. Prisma has no `@map` on these fields (exception: HR + M365 columns, see their entries).
- **M365 routes use raw pg**: `src/app/api/admin/companies/[id]/m365/route.ts` uses raw pg. Column `updatedAt` must be quoted: `"updatedAt" = NOW()` — NOT `updated_at`.
- **M365 columns are snake_case in DB**: The 6 M365 columns (`m365_tenant_id`, `m365_client_id`, etc.) use `@map()` in Prisma schema and ARE snake_case in PostgreSQL. All other Company fields are camelCase in the DB.
- **JSONB columns need ::jsonb cast in raw pg**: When inserting a JSON.stringify() string into a jsonb column via raw pg, use `$1::jsonb` not `$1`.
- **db-pool.ts MUST have SSL config**: The shared raw pg pool in `src/lib/db-pool.ts` MUST include `ssl: process.env.NODE_ENV === 'production' ? { rejectUnauthorized: false } : false`. Without it, all 24+ routes using `getPool()` silently fail to connect in production. This was a regression when consolidating pools — never remove the SSL config.
- **prisma.ts MUST have SSL config**: The Prisma adapter pg pool in `src/lib/prisma.ts` also MUST include the same SSL config. Without it, all Prisma queries fail with "Connection terminated due to connection timeout" in production. Both pool files must always have SSL.
- **DB pools MUST be cached globally (all environments)**: Both `src/lib/prisma.ts` and `src/lib/db-pool.ts` cache their pools on `globalThis`. In serverless, the same isolate handles multiple invocations — without global caching, each invocation creates a new pool, causing connection churn and pool exhaustion. Never change the caching to dev-only.
- **Connection pool exhaustion**: Creating audiences or other bulk operations can exhaust the connection pool. Use explicit `$disconnect()` or connection-aware patterns for batch operations.
- **"too many connections for role `prisma_migration`" = site-wide outage (auth + portal down)**: The runtime connects to Prisma Postgres on the **direct** connection (`DATABASE_URL`, role `prisma_migration`), NOT the pooled `PRISMA_DATABASE_URL` (Accelerate) that `.env.example` documents for the app. That role's connection limit is shared across ALL serverless instances, so total connections = `instances × pool.max`. When it's exceeded, Postgres returns `53300 / P2037` and **everything DB-backed fails at once** — NextAuth (database session strategy) can't read sessions → `AdapterError` → `/auth/error?error=Configuration` ("server configuration" page); the customer portal's `/api/portal/auth/*` 500s with "Network error". A new deploy makes it worse: every cold-started instance ran `instrumentation.ts`'s boot migrations on the same role (now removed for this reason). Mitigations applied 2026-06-30: removed boot-time migrations from `instrumentation.ts`; lowered `pool.max` 5→2 in both `prisma.ts` and `db-pool.ts`. **Durable fix (not yet done): move the runtime onto the pooled `PRISMA_DATABASE_URL`/Accelerate connection** (the repo already has `@prisma/extension-accelerate`; old `*.bak` route files show the intended `new PrismaClient({ ... }).$extends(withAccelerate())` pattern). Immediate operator relief during an incident: restart/scale the database in the Prisma Console (Vercel → Storage → Prisma Postgres → Open in Prisma Console).
- **No hard deletes** — use status fields or `deletedAt` timestamps.
- **Progress should use status, not `completed` boolean**: Task completion is tracked via status (REVIEWED_AND_DONE, NOT_APPLICABLE, ITG_DOCUMENTED), not the legacy `completed` boolean field.

## Serverless, Cron & Resilience

- **All external API fetch() calls MUST have timeouts**: Every `fetch()` call to an external service (Autotask, Graph, Pax8, Datto, Resend, Anthropic, Turnstile, social media) MUST include `signal: AbortSignal.timeout(X)`. Without a timeout, a hung external API blocks the entire serverless function indefinitely. Use 15s for auth/token calls, 30s for data requests. The `src/lib/resilience.ts` module provides `withTimeout()` for wrapping non-fetch operations.
- **Use `src/lib/resilience.ts` for all retry/timeout/circuit-breaker needs**: single source of truth for `withRetry()` (exponential backoff), `withTimeout()`, `withCircuitBreaker()`, `withDbRetry()` (optimized for serverless cold starts), `classifyError()`, and `structuredLog`. Do NOT create ad-hoc retry loops elsewhere.
- **`database` session strategy makes `auth()` a DB round-trip that can return `null` (not throw) under pool contention → false 401s**: `session.strategy = "database"` (auth.ts) means every `auth()` call queries the Session table. A heavy admin page that fans many queries out against the small (`max: 5`) pool can starve that lookup; Auth.js then swallows the adapter error and `auth()` resolves to `null`, so a plain `if (!session?.user) return 401` guard fires a *false* 401 at a logged-in user. Seen on `/api/admin/system-health` as a recurring "HTTP 401 — Failed to load system health" — it's the heaviest dashboard endpoint (~20 concurrent queries), is fetched **twice** per load (`SystemHealthDashboard` + `DashboardStatusCards`' AI card), and auto-refreshes every 60s. Fix: treat a null session as a *retryable* signal (`withRetry`, `shouldRetry: () => true`) and only 401 after retries still yield no session; preserve the "DB genuinely down → proceed" path so the health endpoint can still diagnose outages. Do NOT "fix" by widening the pool `max` in `prisma.ts` (that file's pool config is load-bearing — see Database rules).
- **Cron jobs must NEVER return 500 for transient failures**: Use `classifyError()` from `resilience.ts` and return 200 with `{ transient: true }` for connection/timeout/rate-limit errors. This prevents Vercel from flagging cron invocations as failures and triggering its own alerting. Only return 500 for permanent/validation errors.
- **Cron auth uses Vercel Authorization header**: Cron endpoints authenticate via `Authorization: Bearer <CRON_SECRET>` header (set by Vercel automatically). Don't use secret in query params or URL paths.
- **Health monitor uses sliding window, NOT point-in-time checks**: The health monitor (`/api/cron/health-monitor`) requires 3 consecutive failures to alert and 2 consecutive healthy checks to resolve. It uses the `health_monitor_state` DB table (NOT `health_monitor_alerts` which is legacy). Do not reduce these thresholds — they prevent alert oscillation.
- **Health monitor job names use underscores**: The health monitor checks for `sync_tickets`, `sync_time_entries`, `aggregate_company`, `aggregate_technician` (underscores). Never use hyphens for job names in the DB — the health monitor had a mismatch bug that sent false alerts every 15 minutes until fixed (2026-03-27).
- **Serverless timeout**: 30s max for API routes (blog generation can be tight). The Autotask trigger route uses `maxDuration = 60` since sync can be slow (page size 5 projects/request to stay within timeout). CFO routes (`/api/admin/cfo/data`, `/rebuild`, `/api/cron/cfo-rebuild`) use `maxDuration = 300` — the first full 24-month Sequence pull under the rate gate exceeds 60s (requires Vercel Pro).
- **Self-chaining backfill**: The reporting sync uses fire-and-forget self-chaining — one API call triggers the next batch server-side. A single URL invocation runs all jobs to completion. Don't add polling or retry logic on top.

## API Routes & Security

- **API catch blocks must NEVER return 200 with empty data**: When an API route catches an error, it must return an error status code (4xx/5xx) with an `{ error: 'message' }` body. NEVER return `{ data: [] }` or `{ tickets: [] }` inside a catch block — this makes the UI show "no data" instead of an error message, and the user thinks the feature is broken. If there is legitimately no data (not an error), that should be outside the catch block.
- **Use `checkSecretAuth()` from `src/lib/api-auth.ts` for secret-based route auth**: accepts both `Authorization: Bearer <secret>` headers (preferred — not logged) and `?secret=` query params (legacy — logged in URLs). It checks both `MIGRATION_SECRET` and `CRON_SECRET`. Do not write inline secret checks in new routes.
- **Use `checkCsrf()` from `src/lib/security.ts` on all customer mutation endpoints**: All POST/PUT/PATCH/DELETE endpoints that accept browser form submissions must call `checkCsrf(request)` before processing. Validates Origin/Referer headers. Skips for API clients with Authorization headers and in development.
- **Use `checkRateLimit()` from `src/lib/security.ts` on auth endpoints**: All login, password, and email-lookup endpoints must be rate-limited. Call `checkRateLimit(request)` (or `checkRateLimit(request, { strict: true })` for sensitive endpoints). Returns a 429 response if the limit is exceeded.
- **Never log auth details**: Do not use `console.log` for password validation results, session tokens, signing keys, company slugs in auth context, or env variable names related to credentials. These appear in Vercel function logs which are accessible to anyone with Vercel dashboard access.
- **Never use default/fallback signing keys**: Session signing keys (`ONBOARDING_SIGNING_KEY`, `NEXTAUTH_SECRET`) must come from environment variables. Never provide a hardcoded fallback — it's visible in source code and makes sessions forgeable.
- **Use `NEXT_PUBLIC_BASE_URL` for dynamic URLs in components**: Never hardcode `triplecitiestech.com` in component code that generates links, callback URLs, or form share URLs. Use `process.env.NEXT_PUBLIC_BASE_URL || 'https://www.triplecitiestech.com'` so preview deployments work correctly.
- **CSP is strict**: Adding any third-party resource requires updating headers in `next.config.js` (separate dev/prod policies).
- **ChatGenie widget**: Must use standard `<script>` tag, not Next.js `<Script>` component.
- **forEach return does NOT stop execution**: `array.forEach(cb)` ignores return values inside the callback. If you need early return (e.g., to send an HTTP error response), use a `for` loop or `Array.from().some()`. The middleware had this bug for query param filtering — it was completely non-functional until fixed.

## Testing & CI

- **The e2e gate's first real run (2026-06-12, run 1068) exposed specs that had never executed against a deployment.** Lessons locked in:
  - **Specs must match real route methods.** `/api/tasks` is POST-only, `/api/companies` is POST/DELETE-only (admin pages list via server components, not GETs) — `request.get()` against them returns Next.js's bare 405 (empty body), not the app's 401. Check the route's exported methods before writing an API spec.
  - **`auth.setup.ts` must fail loudly in CI.** Its silent `setup.skip()` when `E2E_TEST_SECRET` was unset let 16 authenticated specs run against a nonexistent storage-state file (ENOENT × 16, cause buried). It now throws in CI when the secret is missing or `/api/test/auth` 404s.
  - **CI needs BOTH GitHub Actions secrets**: `VERCEL_AUTOMATION_BYPASS_SECRET` (or every preview request dies at the Deployment Protection wall — zero runtime logs on the preview is the telltale) and `E2E_TEST_SECRET` (must match the Vercel env var, or authenticated specs can't mint a session).
  - **Third-party console noise on preview domains is expected**: Turnstile (`challenges.cloudflare.com` frame errors — the widget only allowlists production domains) and the MyGlue embed ("A network error occurred"). The no-fatal-JS-errors specs filter these; don't "fix" them by allowlisting `*.vercel.app` in vendor dashboards.
  - **Auth before input validation in routes**: customer ticket timeline/reply returned 400 (missing params) before checking the portal session — unauthenticated callers could enumerate expected params. Session check now comes first (401 wins).

## React & UI

- **Client dashboards must surface fetch failures, not render empty states (2026-06-11)**: the SOC dashboard swallowed non-ok responses (`if (res.ok) setState(...)` and an empty catch) and rendered zeros + "No security alerts" when its three API calls failed — during a deploy-rollover DB blip the operator saw an "empty SOC" and assumed data loss. Same class as the server-side rule "API catch blocks must never return 200 with empty data": a failed fetch must set an error state with a Retry action, never fall through to the empty-data UI. Also note: **deploy rollovers can blip database-backed sessions** — `strategy: "database"` means every `auth()` does a DB read; intermittent Prisma connection errors during rollover surface as 401s on authenticated APIs for a few minutes (observed 19:30–19:39 on 2026-06-11, self-recovered). Check Vercel runtime logs for `prisma:error` before assuming an auth or code regression.
- **useState does not auto-sync with props**: When using `useState(prop)`, the state only initializes on mount. If the prop changes (e.g., via `router.refresh()`), add `useEffect(() => setState(prop), [prop])` to keep them in sync. Applies to all components that receive data as props and store it locally.
- **Every useEffect+fetch MUST have AbortController cleanup**: Create an AbortController, pass `{ signal: controller.signal }` to fetch(), and return `() => controller.abort()` from the cleanup function. Without this, navigating away causes memory leaks and stale state updates. Check for `AbortError` in catch blocks: `if (err instanceof DOMException && err.name === 'AbortError') return`. If the fetch function is also used as an onClick handler, create a parameterless wrapper: `const fetchData = useCallback(() => fetchDataImpl(), [fetchDataImpl])`.
- **overflow-hidden clips absolute dropdowns**: Never use `overflow-hidden` on a parent element that contains an absolute-positioned dropdown (like AssignmentPicker, CommentThread, DueDatePicker). Use `min-w-0` with `truncate` for text overflow instead.
- **Every admin subsection must have a loading.tsx**: Admin routes (`/admin/soc`, `/admin/reporting`, etc.) must have a `loading.tsx` file that shows a skeleton screen. Without it, navigation shows a blank page during data loading, which looks like a crash.
- **Error boundaries must wrap all major layout sections**: Use `AdminErrorBoundary` for admin and `PortalErrorBoundary` for portal. Without them, a single component crash blanks the entire section.
- **Mobile matters**: Every UI change must account for `sm`/`md`/`lg` breakpoints. Never ship desktop-only layouts.
- **ContactsList has a `mode` prop**: `'both' | 'clients-only' | 'staff-only'`. `/admin/contacts` uses `clients-only`, `/admin/staff` uses `staff-only`. Don't render ContactsList without a mode if you want only one tab visible — the legacy `'both'` mode still shows the tabs.
- **Demo mode null safety**: All anonymization functions (`anonCompany`, `anonPerson`, `anonEmail`, `anonTicketTitle`) return `''` for null/undefined input. The `title` callback in DemoModeProvider also guards: `anonTicketTitle(t || '')`. This prevents React rendering crashes when demo mode is active and data fields are undefined.
- **Status badges**: Always display as `Status: <label>` (e.g., "Status: In Progress").
- **Marketing pages**: All `/admin/marketing/*` pages must include AdminHeader and the ambient gradient background.

## CI/CD & Deploy Pipeline

- **Auto-merge to main is gated (2026-06-09; e2e made non-blocking 2026-07-10)**: `.github/workflows/auto-merge-claude.yml` merges when secret-scan + quality gates pass (lint, schema-drift, `next build`, unit tests via the reusable `.github/workflows/quality-gates.yml`, ~5-8 min). The full Playwright e2e suite still runs against the commit's Vercel preview but **no longer blocks the merge** — owner direction 2026-07-10 to cut the 15-45 min merge latency. **A red `e2e-preview` job on a merged commit = production is already live with whatever the suite flagged — treat it as a live incident signal, not noise.** Do not remove secret-scan/quality from the merge job's `needs`/`if` — the fully ungated version shipped broken commits straight to production.
- **`[skip-e2e]` in the commit message skips the (informational) e2e run** — e.g. Vercel GitHub integration down, no preview deployments being created. Secret-scan and quality gates can never be skipped. Record any use in `docs/session-summary.md`.
- **The e2e job finds the preview via the GitHub Deployments API** (Vercel posts deployment statuses). If Vercel's GitHub integration is disconnected, the job times out after 30 min (merge is unaffected since 2026-07-10); fix the integration or use `[skip-e2e]` to silence it. Transient "unable to fetch required git information" Vercel errors (seen 2026-07-10) resolve on a retry push.
- **Authenticated e2e in CI needs the `E2E_TEST_SECRET` repo Actions secret** (Settings → Secrets and variables → Actions). Without it, `auth.setup.ts` skips authenticated specs gracefully — unauthenticated coverage still gates the merge.
- **Vercel Deployment Protection breaks the entire e2e-vs-preview gate (2026-06-11)**: when Deployment Protection is enabled on the Vercel project, every preview route (pages AND `/api/*`) returns **401 + Vercel's auth HTML** to non-browser-authenticated requests. Symptom: every `page.goto()` spec fails in ~2s and retries 3× (the 45-min job timeout is the failure-storm itself), the "nonexistent page returns 404" spec gets 401, while lenient "200 or 401" API specs still pass — so the suite looks "flaky" when it's actually 100% walled. No branch can pass; do not burn cycles re-kicking. Fix: operator creates a **Protection Bypass for Automation** secret (Vercel → staging project → Settings → Deployment Protection), adds it as the `VERCEL_AUTOMATION_BYPASS_SECRET` GitHub Actions secret, and CI/Playwright sends `x-vercel-protection-bypass: <secret>` + `x-vercel-set-bypass-cookie: true` headers. Quick triage check for "is the gate walled?": `curl -s -o /dev/null -w "%{http_code}" https://<preview>/no-such-page` — 401 means walled (a healthy preview gives 404).
- **`next build` in CI uses dummy env vars** (`DATABASE_URL`, `PRISMA_DATABASE_URL`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL` — see `quality-gates.yml`). All DB-touching pages are dynamic, so nothing queries at build time. If a future change makes a page static (SSG) with a DB query, the CI build will fail — make the page dynamic rather than adding real credentials to CI.
- **Schema drift check runs in three places**: CI (`quality-gates.yml`), the Vercel build (`vercel.json` buildCommand), and local `npm run build`. It validates raw SQL column references against `schema.prisma` and that schema fields have migrations — it is the automated guard for the #1 production-killer. Never remove it from the build path.
- **Expand-contract migrations**: schema changes shipped alongside code must be additive only (ADD COLUMN / CREATE TABLE / CREATE INDEX), applied before the code goes live. DROP/RENAME happens in a *later* deploy after production code stops referencing the old name. This keeps Vercel instant-rollback safe at all times.
- **`_prisma_migrations` retrofit**: `docs/runbooks/MIGRATIONS_RETROFIT.md` is the operator-run procedure that makes `prisma migrate deploy` real and eliminates the manual POST-after-deploy step. Until executed, `vercel.json` must NOT contain `prisma migrate deploy` (it would fail every build — migrations can't apply over already-existing tables without the baseline).

## Autotask Integration — Key Knowledge

Primary external data source for companies, projects, phases, and tasks. The owner considers Autotask data authoritative. See `docs/reference/AUTOTASK_SYNC.md` for full docs.

**Sync endpoint**: `GET /api/autotask/trigger?step=<step>` — authenticate with `Authorization: Bearer <MIGRATION_SECRET>` (preferred) or `?secret=<MIGRATION_SECRET>` (legacy, URL-logged — avoid)

**Steps** (run in order):
1. `cleanup` — delete AT-synced companies with no projects
2. `companies` — sync companies that have projects in Autotask
3. `projects&page=1` — sync projects with phases, tasks, descriptions, notes (5/page, paginated)
4. `contacts` — sync contacts (auto-creates table if missing)
5. `merge` — deduplicate companies (keeps AT-synced, absorbs non-AT duplicates)
6. `resync&page=1` — re-fetch phases+tasks for existing AT projects (fixes empty phases)
7. `diagnose` — show raw API response for debugging

**Critical bugs fixed (do NOT reintroduce)**:
- **Never silently catch phase/task API errors** — the original code had `try { } catch { /* no phases */ }` which hid all failures and made it look like projects had no data. Always report errors.
- **Task status values must be distinct** — Autotask uses picklist values: 1=New, 4=In Progress, 5=Complete, 7=Waiting Customer. The old code had both IN_PROGRESS and COMPLETE mapped to `5`, so tasks never showed as complete.
- **company_contacts table may not exist** — the contacts sync auto-creates it via raw SQL if missing. Don't bail out with "run migration first".

**Key files**: `src/lib/autotask.ts` (API client, types, status mappers), `src/app/api/autotask/trigger/route.ts` (multi-step sync endpoint), `src/app/api/autotask/status/route.ts` (sync history viewer).

**Data flow**: Autotask → AutotaskClient (REST API) → syncCompany/syncProject/syncPhase/syncTask → Prisma models

**Autotask gotchas**:
- **Multiple entity paths**: Tasks can be at `Projects/{id}/Tasks`, `ProjectTasks`, or `Tasks`. Phases at `Projects/{id}/Phases` or `Phases`. The client tries multiple paths with fallbacks.
- **Task status values are instance-specific**: Use the `?step=diagnose` endpoint to see actual picklist values. Don't hardcode assumptions.
- **Duplicate companies**: Autotask sync can create duplicates of companies that already existed locally. Use `?step=merge` to deduplicate (keeps AT-synced company, moves projects from non-AT duplicate).
- **Empty phases after sync**: If phases show up empty, the task API likely failed. Use `?step=resync` to re-fetch and check `?step=diagnose` for API errors. Resync also cleans up genuinely empty phases and updates phase statuses based on task completion. (Historically the client silently returned truncated results when a pagination page failed — since 2026-06-09 `queryAll` retries transient page failures and **throws** if a page still fails, so truncation surfaces as a sync error instead of quietly missing data.)
- **Client retry policy (2026-06-09)**: `AutotaskClient` wraps GET/query/PATCH in `withRetry` from `resilience.ts` (2 retries, 1s base backoff — retries 429/5xx/timeouts only; 404/400 surface immediately so entity-path fallback chains stay fast). **POST is deliberately NOT retried**: creates aren't idempotent and a retry after an ambiguous timeout would duplicate notes/time entries. Don't add retry loops on top in callers.
- **Ticket queries use `includeFields`** (`TICKET_QUERY_FIELDS` in `autotask.ts`): without it Autotask returns ~80 fields + userDefinedFields per ticket. The list must stay in sync with the `AutotaskTicket` interface — if you add a field to the interface, add it to the constant or it will come back `undefined` at runtime while type-checking fine.
- **Custom ticket statuses break ID-based closed checks (2026-06-09)**: the operator creates custom statuses in Autotask (e.g. "Complete - No Notify") which get NEW picklist IDs — the static resolved set `[5, 13, 29]` in `src/lib/tickets/utils.ts` undercounts closed tickets. `isResolvedStatus(status, statusLabel?)` is label-aware; ALWAYS pass the status label (live picklist for customer views, synced `statusLabel` for DB rows). The reporting layer (`updateStatusClassification`) was already label-driven and unaffected.
- **Write-back: PATCH vs POST**: Task status PATCH returns 404 on all 3 entity paths for this Autotask instance. However, notes (POST `TaskNotes`) and time entries (POST `TimeEntries`) work fine. The task PATCH API (`/api/tasks/[id]`) returns `autotaskSyncFailed: true` when the write-back fails so the UI can warn the admin.
- **`?step=companies` only syncs Autotask companies that have projects**: Customers without an active project in AT won't be pulled in via that step. - **`nextPageUrl` GET returns 405 on `includeFields` queries (2026-06-16)**: `queryAll` paginates by following `pageDetails.nextPageUrl` with a **GET**, which this Autotask zone rejects with HTTP 405 (*"The requested resource does not support http method 'GET'"*) whenever the original query used `includeFields`. ## Autotask ticket reads must never support a false absence claim (2026-07-30)

**The defect**: `autotask_ticket_notes` returns Autotask `TicketNotes` and **structurally excludes time entries**. On ticket 34648 technician Ghenel Bacalla logged 2.67 hours of completed provisioning work as **time entry 13188** (2026-07-29 12:05–14:45). It was invisible to the notes read, and the assistant told the owner there was no update from Ghenel showing the work finished. The ticket payload already carried the contradiction — `lastActivityDate` was `2026-07-29T14:48:47` while the newest returned note was `12:08:22` — and nothing compared the two. **This is a false-accusation risk against an employee, so it is a correctness bug, not a nicety.**

**The fix** (`src/lib/autotask-activity.ts` — pure, locked by `autotask-activity.test.ts`):
- **`autotask_ticket_activity(ticketId)`** is now the ONLY read that should ground a statement about whether work was done. It merges **TicketNotes + TimeEntries + TicketAttachments** into one chronological timeline, each item tagged with source entity, author (resource name + email, or the customer contact), timestamp, and customer-visible vs internal.
- **Every ticket read** (`autotask_get_ticket`, `…_by_number`, `autotask_search_tickets`, `autotask_company_tickets`, `autotask_ticket_notes`, `autotask_ticket_time_entries`, `autotask_ticket_activity`) returns `lastActivityDate` plus a computed **`activityGap`**, true when `lastActivityDate` postdates the newest item that read returned, with a warning naming the tool to call.

**Non-obvious things worth keeping**:
- **A timestamp gap check ALONE is not enough.** On 34648 today the newest note is *newer* than both time entries, so a pure timestamp comparison reports no gap while the completed work is still invisible to a notes read. `autotask_ticket_notes` therefore ALSO carries an unconditional structural notice (`TICKET_NOTES_EXCLUSIONS`) that it returns notes only and must not ground a "no work done" claim. Both signals are needed; a test pins this exact case.
- **No tolerance window, deliberately.** Autotask stamps `lastActivityDate` in the same transaction and async workflow/notification notes land a second or two later, so small positive gaps are common (34648 shows a 3s one). A tolerance would suppress those *and* real gaps. Given the failure mode, the asymmetry is clear: a spurious "go check the timeline" costs one tool call, a missed gap costs someone a false accusation. `gapSeconds` is published so a reader can tell 3s of skew from 2h 40m of unretrieved work.
- **`activityGap: null` means NOT MEASURED** (the ticket carried no `lastActivityDate`) and is never collapsed to `false` — an unmeasured check must not read as a clean bill of health.
- **Order by RECORD time, not work time.** The timeline sorts on a note's `createDateTime`, a time entry's `createDateTime` and an attachment's `attachDate`, because `lastActivityDate` is a record-activity stamp — ordering time entries by `startDateTime` would compare unlike things and mis-report the gap. Each time entry still carries its work window (`dateWorked` / start / end / hours). `TimeEntryView.createDateTime` was added for this.
- **`TimeEntries` has NO `publish` field** (verified live: *"entityInformation for TimeEntries lists no field named publish"*), so time-entry visibility reports `scope: 'unknown'` **with the reason** rather than guessing internal or customer-visible. Inventing a vendor capability is the exact class of bug this module exists to kill.
- **`TicketAttachments` non-queryable fields**: `creatorType`, `data` and `fileSize` [error when queried](https://ww1.autotask.net/help/DeveloperHelp/Content/APIs/REST/Entities/TicketAttachmentsEntity.htm) — never put them in `includeFields`. Querying by `ticketID` does return attachments parented to the ticket's notes and time entries, per the same page.
- **A failed source is NAMED, not silently empty**: `sourcesUnavailable` reports any source whose query failed, so a broken attachment query can never read as "no attachments".
- Collection reads (`search_tickets`, `company_tickets`) carry ONE top-level `activityGapAdvisory` plus a per-ticket boolean — 2000 copies of the same sentence is how a warning gets skimmed past. Both changed shape from a bare array to `{ count, activityGapAdvisory, tickets[] }`.

## IT Glue Integration — Key Knowledge

- **Document section writes land on the DRAFT, not the published version (2026-07-05)**: `POST/PATCH document-sections` (and therefore `itglue_add_document_section` / `itglue_update_document_section`) update the document's draft revision only. The published snapshot — what techs see in IT Glue and MyGlue — is untouched until the document is published (`PATCH /documents/{id}/publish`, exposed as `itglue_publish_document`). An "updated" SOP that skips the publish step still shows the old content to everyone. Learned the hard way updating the client offboarding SOPs: the API echoed the new content while the live page kept the 2024 version. Also note: the sections API reads the draft, so a read-back "verification" cannot detect the unpublished state — and publishing pushes the ENTIRE current draft live, including anyone's earlier unpublished edits.
- **Archived documents still appear in our content index**: `itglue_doc_index` (and name search) can return documents that are archived in IT Glue, where techs won't find them in normal browsing. If an SOP update matters, confirm the target document isn't archived.
- **IT Glue PATCH is destructive for flexible assets** — omitted traits are deleted; writes go GET-merge-PATCH (`updateFlexibleAsset`). Same class of quirk as the UniFi Integration API's full-object PUT.
- **The API CAN rename, relate, attach, and publish (verified against developer docs + the official PowerShell wrapper, 2026-07-08)**: rename = `PATCH /documents/{id}` (`attributes.name` — metadata, applies immediately, outside the draft cycle); Related Items = `POST /{sourceType}/{id}/relationships/related_items` with `destination_type` as the human LABEL ("Document") not the URL form, and only the link's `notes` are editable afterwards; attachments = `POST /{type}/{id}/relationships/attachments` with base64 `attachment.content` + `file_name`, **10 MB cap**; publish = the docs say `POST /documents/{id}/publish` while our client historically used PATCH — `publishDocument()` now tries POST, falls back to PATCH on 404/405, and **verifies via GET that `published-at`/`draft` flipped** (never trust a publish call without the read-back). Document publish state is readable: `draft`, `document-status`, `published-at`, `published-by`. What remains human-only in the UI: deleting documents (deliberately not exposed as a tool) and anything on the /passwords resource (excluded on both ends of relate/attach by policy).
- **In-tenant verification results (2026-07-08, doc 24236262)**: the documented `POST /documents/{id}/publish` is REJECTED on our tenant — the legacy **PATCH is what works** (`methodUsed: "PATCH"` from the fallback; keep the fallback in case Kaseya flips it later). And Related Items are **bidirectional from ONE call** — the docs' directional model is wrong in practice; the inverse call 422s with "a similar or inverse relation already exists" (a 422 there means the link already exists, not a failure).
- **Document folders ARE in the public API — but ONLY as org-nested routes (verified against developer docs, 2026-07-16)**: list/show/create/update = `GET|POST /organizations/:org_id/relationships/document_folders(/:id)`; there is NO top-level `/document_folders` index (the only top-level route is bulk PATCH). Folder attributes are dasherized: `name`, `parent-id` (null = top-level), `ancestor-ids` (path from root), `restricted`, `my-glue`, `documents-count`. Create body = `{ data: { type: 'document-folders', attributes: { name, 'parent-id'?, restricted:false } } }` (org inferred from the URL). **The folders index default is the OPPOSITE of the documents index**: omitting `filter[parent_id]` returns ALL folders (and `null` means "no filter"), while omitting `filter[document_folder_id]` on documents returns ROOT-ONLY documents — don't carry one habit to the other. `filter[parent_id]` takes a SINGLE value; comma-separated values silently return empty. `0` = top-level-only on both. ~~Moving a document = `PATCH /documents/:id` with `document_folder_id`~~ — **WRONG, corrected 2026-07-29: `document_folder_id` is create-only and IT Glue silently drops it on PATCH. See the next bullet.** Rename (`attributes.name`) IS a working PATCH: metadata, applies immediately, outside the draft/publish cycle, ID-based inline links survive. Attribute-key note: IT Glue **normalizes hyphen/underscore on writes** — this client writes `organization_id` (underscore) for documents and `organization-id` (hyphen) for flexible assets and both work; folder create follows the documented hyphenated `parent-id`. Connector tools: `itglue_list_document_folders`, `itglue_create_document_folder`, `itglue_move_document` (**does not work — see the next bullet**); folder DELETION is deliberately not exposed (UI-only), same policy as document deletion. `itglue_create_document` now requires resolving the destination folder first — SOPs never default to the org root. NOTE 2026-07-16: two parallel sessions shipped this feature minutes apart with the SAME three tool names; the implementations were unified in the follow-up merge (rich folder shape + parentId filter + meta-based paging + verified move) — if tool output looks minimal (`parentFolderId`-only), the caller is on the pre-unification deploy.
- **A DOCUMENT CANNOT BE MOVED BETWEEN FOLDERS THROUGH THE API — folder placement is CREATE-ONLY (2026-07-29)**: IT Glue's developer reference marks `data[attributes][document_folder_id]` "**Not permitted in PUT/PATCH, optional in POST**" on `PATCH /documents/:id` AND on the bulk `PATCH /documents`, while documenting and honouring it on `POST /documents`. IT Glue does not *error* on the rejected attribute — it drops it and returns **200 with the document unchanged**, which is why `itglue_move_document` reported `moved:false` with no error and the defect survived twelve days across two sessions (doc 24262329 → folder 5301326 on 2026-07-17; doc 24227609 "TCT Documentation Standard (START HERE)" → folder 6255494 on 2026-07-29). What changed: `ItGlueClient.updateDocument` types `documentFolderId` as `never` and throws if one reaches it, `itglue_move_document` **writes nothing** and returns `UPSTREAM_UNSUPPORTED` / `fixableBy: vendor` with the document's current folder in `details`, and `itglue_rename_document` **refuses the whole call before renaming** if `documentFolderId` is supplied (it used to accept and silently ignore it) so there is never a half-applied write. Evidence lives in one exported constant, `DOCUMENT_FOLDER_MOVE_UNSUPPORTED` in `src/lib/it-glue.ts`, cited by the tools and `known-limits.ts`. **The only two things that work: set `documentFolderId` at CREATE time, or have a human move it in the IT Glue UI (Documents list → tick → Move).** Standing lesson: a vendor that answers 200 while ignoring your attribute produces a silent no-op, so a write tool must read back and must return a hard failure — `moved:false` inside a success envelope is indistinguishable from a connector bug and invites retries.
- **IT Glue rate limit**: 3,000 requests per rolling 5 minutes → 429; page size max 1,000; idle API keys auto-revoke after 90 days.

## M365 Multi-Tenant Onboarding

Customer M365 integration supports two modes that coexist on the `companies` table:

- **`legacy` (default for existing rows)** — customer creates their own app reg in their Entra tenant; `m365_tenant_id` + `m365_client_id` + `m365_client_secret` all stored on the company row.
- **`multi_tenant` (default for new onboardings)** — customer Global Admin grants tenant-wide consent to TCT's published `TCT Customer Portal` app reg (in the TCT tenant). Only `m365_tenant_id` is stored; client_id/secret come from `M365_PORTAL_CLIENT_ID` / `M365_PORTAL_CLIENT_SECRET` env vars at runtime.

The mode is `companies.m365_consent_mode`. `m365_consent_granted_at` is stamped by the consent callback.

**Consent flow routes:**
- `GET /api/admin/m365/consent?companyId=…` — initiates Microsoft `/adminconsent` (scoped to `organizations`, work tenants only). Requires TCT staff session.
- `GET /api/admin/m365/consent/callback` — Microsoft redirect target. Validates HMAC state, blocks tenant double-binding, writes the tenant link + flips mode.

**At runtime**, all Graph callers go through `getTenantCredentials(companyId)` / `getTenantCredentialsBySlug(slug)` in `src/lib/graph.ts`. The branch on `m365_consent_mode` is invisible to downstream callers (HR, cron, forms, compliance) — they just get a `TenantCredentials` object. **Downstream Graph callers must NOT read the per-tenant columns directly.** Check `m365_consent_mode` if you need to branch.

**Customer portal SSO** (`/api/portal/auth/login` + `/callback`) branches on `m365_consent_mode`: multi-tenant uses `M365_PORTAL_CLIENT_ID/SECRET`, legacy uses the per-tenant fields.

**The onboarding wizard** (`/admin/companies/[id]/onboard`) has 5 steps: Autotask Sync → M365 Connection (admin consent) → Test Connection → Manager & Invite → Finalize. Step 1 has an inline Autotask company search/link UI when `autotaskCompanyId` is null. Step 4 fetches contacts and chains role-update + send-invite in one click.

**Onboarding gotchas**:
- **Wizard step status must derive from durable DB state**: stepStatus[N] initial values should reflect what's persisted (e.g. step 2 checks `m365_consent_granted_at` for multi_tenant, step 4 checks for an existing `CLIENT_MANAGER` contact with `INVITED/ACCEPTED`). Don't rely on in-session button clicks alone — the user will refresh, deep-link, or come back tomorrow and expect the sidebar to be accurate.
- **TECHNICIAN role can invite customers and manage portal roles**: As of session 8, TECHNICIAN holds `invite_customers` and `manage_customer_roles` so techs running the wizard's Manager & Invite step don't hit Forbidden. Sensitive scopes (`impersonate_customer`, staff role management) remain admin-only. `/api/contacts/invite` GET/POST/PATCH use granular `hasPermission()` checks — not role arrays — so per-user `permissionOverrides` are honored.

## HR Employee-Relations records → TCT's OWN SharePoint (MCP connector)

The connector's `hr_er_log_append` and `hr_file_document` tools write to TCT's **own** HumanResources SharePoint site (`triplecitiestechcom.sharepoint.com/sites/HumanResources`). Modules: `src/lib/hr/employee-relations.ts` (Graph client + ops), `src/lib/mcp-hr-tools.ts` (tool registration). Added 2026-07-15.

- **Dedicated, least-privilege app — do NOT reuse the AZURE_AD staff-SSO app.** These tools authenticate as a separate single-tenant Entra app holding only **`Sites.Selected`**, granted the `write` role to the ONE HumanResources site. This is a THIRD Graph client on purpose (alongside `graph.ts` = customer tenants and `graph-tct.ts` = own-tenant SSO app): it keeps an internet-reachable file-write credential out of the SSO/PTO/CFO secret. Env: `HR_RECORDS_TENANT_ID/CLIENT_ID/CLIENT_SECRET`. Kill switch `CONNECTOR_HR_WRITES_ENABLED` (tools are dormant unless it's exactly `'true'`).
- **`Sites.Selected` + admin consent grants ZERO access on its own.** You MUST also grant the app the `write` role on the specific site: `POST /sites/{siteId}/permissions` with `{ roles:["write"], grantedToIdentities:[{ application:{ id, displayName } }] }`, run by a SharePoint/Global admin (delegated `Sites.FullControl.All` — e.g. Graph Explorer or `New-MgSitePermission`). This is what scopes the app to just the HR site.
- **NON-OBVIOUS: the Excel workbook API DOES work app-only here.** MS Learn's workbook pages say "Application: Not supported" and list only delegated scopes — that applies to `/me` and USER-SHARED files. For an **org-owned SharePoint site**, an app-only token with `Sites.Selected` granted to that site drives `POST /workbook/tables/{name}/rows` etc. fine, and does **not** require `Sites.ReadWrite.All`/`Files.ReadWrite.All`. **A 403 on a workbook call almost always means the per-site grant above was never applied — not a code bug** (the tool's error message says as much).
- **Direct writes, not staged.** A log append / doc filing is low-risk and the human already approved the text in chat, so these bypass the staged-approval gate — but every write is `structuredLog`-audited (actor email + action + target ids + outcome; never PII bodies, file contents, or secrets) and read-back verified.
- **IDs are computed, never input.** `ER-NNNN` (log) = max existing + 1 read live from the table; `ER-DOC-NNNN` (filed docs) = max across central-folder filenames + 1. The append is an Excel *table* row-add (atomic, never overwrites); if no table exists the tool converts the log worksheet's used range to one on first run. Residual ID-collision from truly-concurrent appends is detected on read-back and surfaced as a warning, not silently.
- **Log input is sanitized to plain text** (emojis/pictographs/control chars stripped) and dates stored `YYYY-MM-DD` Eastern — standing rule for `Employee Relations Log.xlsx`.
- Live-verified workbook location (2026-07): driveId `b!nhXC-…LAt0W`, itemId `01PWEAC3YF6BMXSB74CNDZ2PTOBVZZK5CU`; overridable via `HR_ER_DRIVE_ID`/`HR_ER_ITEM_ID`, and resolved dynamically by folder path as a fallback if the file is moved.
- **Address Excel tables by NAME, never the braces-GUID `id`** (bug found on the first prod call, 2026-07-16). `GET /workbook/tables` returns an `id` like `{426A5E03-…}`; putting it in a path with `encodeURIComponent` (`%7B…%7D`) makes every follow-up call (`/columns`, `/rows`) 404 `ItemNotFound`. Use the table `name` (`Table1`) — the clean half of Graph's `/tables/{id|name}` key. `tableSeg()` in `employee-relations.ts` enforces this. Also: `resolveLogTable` finds the ER table by its "Entry ID" header (wherever it lives) and, if none, converts the ER worksheet's used range — it never appends to an arbitrary unrelated table.
- **The appended row's WIDTH and ORDER must be read from the table's LIVE header row — never hardcoded** (bug found in prod 2026-07-30, `hr_er_log_append` failing on **every** call). `ER_COLUMNS` was a hardcoded 14-entry list; the owner had added a 15th column, **"Meeting with Tech"** (free text for what the technician said when the issue was discussed — populated by hand on ER-0001 and ER-0004). Graph answered every append with `400 InvalidArgument — "The number of rows or columns in the input array doesn't match the size or dimensions of the range."` The root cause is not the missing column, it is the **hardcoding**: this workbook is a human's document that the owner edits, so any tool that fixes its shape in code guarantees a future outage the next time a column is added. Now: `readTableShape()` reads `/workbook/tables/{name}/columns` at call time, and pure `planErRow()` maps inputs onto the live headers — width is `liveColumns.length` **by construction**, a live column no parameter fills is padded `''` and reported in `unmappedColumns`, and header matching is case/spacing/punctuation-insensitive (`normalizeHeader`, so `Role/Status` still maps to `Role / Status`) with per-field aliases. `ER_FIELDS` now says only *which headers we have content for* — **not the row width**. Locked by tests that append against a 16- and 17-column sheet.
- **Sort table columns by the API's own `index`** before building a positional row. The row is written by position, so trusting the response order would silently write values into the wrong columns.
- **Read-back verification must read the Entry ID at its LIVE column index**, not `values[0][0]` — the Entry ID column need not be first once a human can reorder the sheet.
- **`ER-####` (log) and `ER-DOC-####` (documents) numbering have legitimately DIVERGED and neither may be inferred from the other.** As of 2026-07-30 the log was at ER-0004 while filed documents were at ER-DOC-0002, because two entries (ER-0003, ER-0004) were logged without a filed document. Each is computed from its own source: the Entry ID from the sheet's own Entry ID column, the doc number from the central folder's filenames. Assuming "row N ↔ doc N" would have assigned the wrong id.
- **Excel tables carry NO required-column metadata and Graph reports none** — so "this column is required" can only be a **header-text convention**, never a fact read from the workbook. A column whose header ends in `*` or contains `(required)` that no tool parameter can fill fails the append with a structured `NOT_IMPLEMENTED` envelope naming the column; anything unmarked is padded blank. The markers are deliberately narrow: a bare `required` would false-positive on a column named "Required Action", and a spurious hard failure here blocks the owner from logging a real HR issue.
- **The mirror-image failure is also guarded:** if a column the tool has *content* for disappears from the sheet, appending would silently discard what the human wrote. A missing column for a mandatory field (`contentCritical` in `ER_FIELDS`) is a structured `PRECONDITION_FAILED` naming the column; a missing optional column, or a missing column whose value was empty, is only a warning — nothing was lost.
- **The HR surface now returns the structured failure envelope** (`toolFailure(..., { surface: 'hr_sharepoint' })`), retrofitted 2026-07-30 for exactly this bug: the raw Graph 400 named no column, routed to nobody, and read as a transient glitch. IT Glue / UniFi / Datto RMM are still un-retrofitted.
- **`hr_er_log_columns` is the read-only diagnostic** — reports the live header row, the column count, what maps, what would be left blank, and the next Entry ID, **without writing a row**. This is what was missing on 2026-07-30: there was no way to inspect the sheet's shape except by attempting an append and reading the failure.
- **Caveat — a padded blank is a literal empty string.** If someone adds a *calculated/formula* column to the log table, the append writes `''` into it rather than letting Excel fill the formula. Not observed in this workbook (no formula columns today); if one is ever added, that column needs handling rather than padding.
- **Connector tool list caches at connect time** — after deploying new connector tools, disconnect/reconnect the connector in Claude for them to appear.

### Updating an existing row — `hr_er_log_update` (2026-07-31)

- **Half-finished rows were structural, not accidental.** `hr_er_log_append`'s own `meetingWithTech` description tells the caller to leave the field unset until the conversation with the technician has happened — which *guarantees* it needs filling later. Same for `followUpStatus` when an item closes and `linkedDocument` when a write-up is filed afterwards. There was no update path, so those rows stayed stranded and a human hand-edited the workbook. `hr_er_log_update` patches ONE existing row located by Entry ID.
- **It must never be able to append.** A duplicate row inflates the subject's disciplinary record — the one failure mode this log cannot tolerate. An Entry ID that does not exist is a `PRECONDITION_FAILED` listing the ids that DO exist, never a fallback to append; the tool description says "NEVER creates a row" so a downstream Claude does not reach for `hr_er_log_append` when it means to update.
- **Two Entry IDs the same = refuse, never guess.** Both row indices (and their sheet rows) go in the evidence. Patching the wrong one attaches text to the wrong incident, and there is no safe tiebreak.
- **Entry ID and Date Logged are excluded BY CONSTRUCTION, not by a runtime check.** `ER_UPDATABLE_FIELDS = ER_FIELDS.filter(kind !== 'computed')`, and the tool's input schema is exactly `entryId` + those fields + the two append flags — so no parameter capable of carrying either value exists. Entry ID is the key; Date Logged records when the entry was **created**, not when it was edited. `planErPatch` still refuses them if they somehow arrive (belt and braces), and a test pins the schema key set.
- **Patch SINGLE CELLS, never the row.** Graph's `PATCH /tables/{name}/rows/itemAt(index=N)` takes the whole row's values, which would rewrite every cell — replacing any formula in the row with a computed value and touching cells the caller never named. Instead: read `/dataBodyRange?$select=address,values` for the absolute address, then `PATCH /worksheets/{sheet}/range(address='<cell>')` once per changed column. "Only the named columns" has to mean the others are **not written at all**, not written back with the same value.
- **A missing target column is a HARD failure here, unlike on append.** Append pads an absent optional column with a warning because nothing was lost; update was explicitly *told* to write that cell, so a partial patch would leave the row in a state neither the caller nor the sheet describes. Nothing is written at all — `PRECONDITION_FAILED` naming the column and the live header row, pointing at `hr_er_log_columns`.
- **Verified against the Entry ID, not a row position.** The grid read and the cell writes are separate calls, so a concurrent insert could shift the row between them. The Entry ID cell is re-read at the exact address before writing (refuse if it moved), and the read-back re-locates the row by Entry ID afterwards — if its index changed, the warning says the writes may have landed on a different row and to check both. `verified` is never true without a confirming read.
- **A date-formatted column returns a SERIAL, not the text you wrote.** Read-back compares strings, plus one computed equivalence: a `YYYY-MM-DD` expectation matches a numeric cell whose Excel serial converts to that date (`excelSerialToYmd`, defined only from serial 61 / 1900-03-01 — serials 1–60 sit inside Excel's deliberate 1900-leap-year bug, where 60 is a date that never existed, so it returns null rather than inventing one). Without this, every date patch would report `verified: false` and train the reader to ignore the flag; with a looser rule, `verified` would stop meaning anything.
- **Append mode accumulates, replace mode is the default.** `appendToSummary` / `appendToMeetingWithTech` add the new text on a new line so a follow-up conversation does not erase the first one. The join happens AFTER `sanitizePlainText` (which strips control chars, newlines included) and the existing cell value is never re-sanitized — otherwise the newlines already in the cell would be destroyed by the write that adds one. Appending a line the cell already contains is warned about, not silently skipped: this tool never drops what a human wrote.
- **An explicit empty string CLEARS a cell; an absent field leaves it alone.** Those are different instructions and `suppliedErPatchValues` keeps them distinct by *presence*, not truthiness. A clear is warned about with the old value quoted.
- Live shape confirmed read-only via `hr_er_log_columns` on 2026-07-31: `Table1`, the same 15 columns in order, 5 rows, next id ER-0006. **No live write smoke test was run** — there is no non-production copy of this workbook, and the real HR log is not a test target.

(The old note here that `/api/v2/account/devices` "returns only a subset of devices" was actually the 0-indexed-pagination bug — see the Datto RMM section: `page=1` is the SECOND page, and the client used to start there.)
- **SOC real-time ingest**: `/api/soc/ingest` (Autotask Extension Callout target) pulls one ticket via `syncSingleTicket` and triages immediately; hourly `soc-triage` cron is the safety net. - **SOC assessment must not silently fall back to screening**: the cross-stack assessment uses `max_tokens: 8000` (4096 truncated the JSON → parse failure → silent revert to the old "SOC AI Triage" note). On failure the engine builds a degraded `SocAssessment` from evidence so the new layout always renders. Auto-posts the internal note only when `!dry_run && auto_post_internal_note`.
- **Classification/confidence are the LLM's, but deterministic guardrails run AFTER it in code** (`applyGuardrails` in `src/lib/soc/engine.ts`). The assessment was overconfident toward "false positive" — it used a high historical FP rate as *reassurance*, conflated clean IP reputation with location, ignored off-hours timing, and claimed high confidence with zero corroboration. Fixes, all in `src/lib/soc`:
  - **Recurrence ≠ reassurance.** `getRecurrenceSignal` replaced `getHistoricalFpRate`; we no longer surface an FP *rate*. A high repeat count reduces NOVELTY only — it never raises benign confidence or lowers risk — and `priorBenignCount` is the agent's OWN prior closes (a self-reinforcing loop fed by `soc_ticket_analysis`), explicitly labeled as NOT corroboration. `recurring_pattern_threshold` (default 3) flags a recurring pattern → tenant root-cause section.
  - **Independent signal axes** (`AssessmentSignals` on the `EnrichmentBundle`, computed in `enrichment.ts`/`rules.ts`, rendered by `SignalBreakdown`): IP reputation (NOT checked — no provider wired in; the model must not assert a clean reputation), geolocation-vs-baseline (from the SaaS Alerts event `ip`/`location`, which enrichment used to drop), event timing (`classifyEventTiming` in `reporting/business-hours.ts`, off-hours weight), recurrence, and corroboration. Reputation and geolocation are different questions — never merged.
  - **Confidence is a function of corroboration.** If no independent telemetry corroborated the alert (RocketCyber detail / Datto RMM device / device-scoped EDR/DNS / known-network match — SaaS events are the alert itself, NOT corroboration), code caps confidence at `confidence_uncorroborated_cap` (default 0.5) and lists what was not checked.
  - **IAM/MFA changes default to "confirm with the user before closing"** unless there is positive benign evidence (`isIdentityChangeAlert` in `rules.ts`). A benign identity-change verdict with no corroboration is downgraded to `suspicious_review` in code.
  - The recommendation must always end with a concrete next action when corroboration is missing. `applyGuardrails` patches the LLM's internal-note header + appends a transparent "AUTOMATED GUARDRAIL ADJUSTMENTS" block so the posted note never contradicts the final disposition. IPv6 source IPs are now extracted (`extractIpv6`) — the old IPv4-only regex dropped them.
- **Identity/MFA alerts pull from the customer's OWN M365 tenant for authoritative confirmation** (`src/lib/soc/m365-identity.ts`, `fetchM365Identity`). Reuses `getTenantCredentials(companyId)` + `graphRequest` from `src/lib/graph.ts`, so it is inherently customer-scoped (never cross-tenant). For an identity-change alert it pulls the Entra **directory audit log** (confirms the change + who initiated it + a remove-then-reregister signature), **sign-in logs** (device/IP/Conditional Access), and the user's **current registered auth methods** (answers "is the account left weakly protected?"). A tenant-confirmed benign re-enrollment (method removed AND a strong method re-registered, strong factor still present) sets `corroboratingTelemetry` → lifts the confidence cap and counts as positive benign evidence; a removal with no re-registration / only a weak factor left stays cautious. Requires `AuditLog.Read.All` + `UserAuthenticationMethod.Read.All` + `Directory.Read.All` consented in the customer's app reg (sign-in logs also need Entra ID P1) — missing perms/tenant surface as a Data Gap, never silence. The affected user's UPN is taken from the SaaS event user or the first email in the ticket text.
- **SaaS Alerts events query must match `customerId` OR `organizationId`** (`getEvents` in `src/lib/saas-alerts.ts`). A bare `customerId.keyword` term silently returned zero events for alerts that genuinely originated from that customer (the list's `id` maps to `organizationId` on the events index in some tenants), so the SOC's SaaS correlation reported "no events" for a SaaS-sourced ticket. Now OR-matches both fields (still single-customer scoped). When still empty, the SOC's data-source note states the queried id(s) + window and recommends an explicit `saas_alerts` mapping at Compliance → Connect Tools (fuzzy name-match may resolve the wrong id).

## Domotz Integration — Key Knowledge

Single client: `src/lib/domotz.ts` (`DomotzClient`, `x-api-key` auth, `DOMOTZ_API_KEY` + `DOMOTZ_API_URL`). OpenAPI spec is fetchable: `GET {DOMOTZ_API_URL}/meta/open-api-definition`. The WAN reliability reporting module (`src/lib/reporting/wan-reliability/`, see `docs/reference/WAN_RELIABILITY_REPORT.md`) consumes it.

- **`getAgents()` / bare `GET /agent` returns only 10 results** — `page_size` defaults to 10, so a single call silently truncates large accounts. The compliance collector's `buildSummary()` already slices to 10; for anything that must see every collector use **`getAllAgents()`** (paginates `page_size`/`page_number`). `GET /agent?display_name=<text>` filters server-side — used for the site typeahead.
- **Outage signal: collector vs device.** For *WAN/ISP* reliability the **collector's** own connectivity is the truest "site internet went down" signal (the collector sits behind the same circuit): `GET /agent/{id}/uptime` (% + `downtime_intervals`) and `GET /agent/{id}/history/network/event` (`CONNECTION_LOST`/`CONNECTION_RECOVERED`). A monitored **device's** `…/device/{id}/uptime` + `DOWN`/`UP` events is LAN-side reachability of that device — useful, but a powered gateway with a dead WAN can still read "UP". The report uses the device signal when a device is chosen, the collector otherwise, and cross-reports both.
- **Uptime endpoints are the authoritative outage source**: `…/uptime` returns `{ uptime (string %), online_seconds, total_seconds, agent_uptime, downtime_intervals:[{start,end}] }`. Prefer `downtime_intervals` over hand-pairing events; fall back to pairing `history/network/event` `DOWN→UP` only when uptime is unavailable (handle open boundaries: leading recovery ⇒ down since window start; trailing failure ⇒ ongoing).
- **History endpoints (`/uptime`, `/history/network/event`, `/history/rtd`, `/history/network/speed`) default to a ONE-WEEK window** (`from`/`to` are ISO-8601). Long ranges (e.g. 90 days) must be **time-chunked and merged** — `requestChunked` (arrays) and `aggregateUptime` (sum online/total, concat intervals) handle this. Don't assume one call returns the whole range.
- **RTD = latency + packet loss in one place**: `DeviceRTDHistorySample` is `{ timestamp, min, median, max (latency ms as strings), lost_packet_count, sent_packet_count }`. Packet-loss % = `lost/sent*100` for samples where `sent>0`. Speed samples are `{ timestamp, values:[downloadBps, uploadBps] }`.
- **Domotz does NOT expose street address or ISP.** `agent.location` is lat/long only; `agent.wan_info` is `{ ip, hostname }` — the public IP and its reverse-DNS hostname. ISP is *inferred* from the hostname (`inferIspFromHostname`) and can be wrong; always allow an override (the report takes customer/site/address/ISP/publicIP as editable inputs).
- **Device event `type` enum**: `IP_CHANGE | CREATED | UP | DOWN`. Collector event `type` enum: `CONNECTION_RECOVERED | CONNECTION_LOST | UP | DOWN`. Device `status` enum: `ONLINE | OFFLINE | DOWN | HIDDEN`.
- All Domotz calls go through `withRetry` (`src/lib/resilience.ts`) — 429/transient back off; never add an ad-hoc retry loop.
- **Reachability ≠ ISP-circuit reliability at a failover site (the big one).** At any site with WAN failover (Meraki MX + Starlink/LTE, SonicWall/FortiGate dual-WAN, etc.), when the primary circuit drops the firewall fails over and BOTH the monitored device AND the collector stay reachable — so Domotz records NO outage. A "100% uptime / SLA-compliant" reading at such a site is a false negative (confirmed at XNG – Montrose: 10 primary drops incl a 17-min outage, reported 100%). The Site Connectivity report (`docs/reference/WAN_RELIABILITY_REPORT.md`) therefore (a) headlines *collector connectivity* (whole-site dark), not "ISP uptime"; (b) shows an SLA pass/fail ONLY for admin-confirmed single-WAN sites; (c) shows a prominent masking caveat for failover-capable/unknown sites; (d) never prints "ISP SLA-compliant"/"no escalation" from reachability alone.
- **`agent_wan_change` (public-IP/ISP change = failover fingerprint) is WEBHOOK-ONLY** — it's a `callbacks` payload on the alert-profile binding, NOT a GET history endpoint, so it cannot be pulled on demand. To detect failovers historically we ingest it: receiver `POST /api/webhooks/domotz` (token `DOMOTZ_WEBHOOK_TOKEN`, always-200 so Domotz doesn't disable the channel) → stored in the shared `compliance_webhook_events` sink with `source='domotz'` (no new event table). Same push-only caveat applies to `agent_status`, `agent_lan_change`, `device_heartbeat_lost`.
- **Domotz reports no data retention or polling cadence** in the API. Don't assume a 90-day request returns 90 days — coverage is measured empirically from `uptime.total_seconds`, and outage durations that cluster at one value are flagged as a poll-interval artifact, not real length.
- **Per-site WAN-mode override** lives in raw-pg `domotz_site_settings` (created by `ensureDomotzSiteSettings()` in `src/lib/domotz-events.ts`) — a raw-pg subsystem table like `soc_*`/`report_*`, NOT a Prisma model, so it needs no `/api/migrations/run` entry.

## UniFi / Ubiquiti Integration — Key Knowledge

Two API surfaces, two clients — do not merge them:
- **`src/lib/ubiquiti.ts`** — cloud Site Manager aggregate reads (`/ea/*`). Known flaw kept for its existing consumers: it swallows errors and returns `null`/`[]`. Do NOT copy that pattern.
- **`src/lib/ubiquiti-proxy.ts`** — per-console **local Network Integration API** through the **Cloud Connector Proxy** (`https://api.ui.com/v1/connector/consoles/{consoleId}/proxy/network/integration/v1/...`, same `UBIQUITI_API_KEY`). Throws typed `UnifiProxyError` (`AUTH_FAILED` / `CONSOLE_OFFLINE` / `FIRMWARE_UNSUPPORTED` / `NOT_FOUND` / `RATE_LIMITED` / `TIMEOUT` / `BAD_REQUEST` / `UPSTREAM_ERROR`) — empty and failed must stay distinguishable, or an offline console reads as "zero clients" and a tech closes a ticket on false data.

Key facts (verified against the official OpenAPI spec, v10.1.84, July 2026):
- **Feature availability is firmware-gated**: devices/clients/actions/vouchers since Network app 9.1; networks/WLANs/zones/ACL/traffic-lists since 10.0.162; **firewall policies, DNS policies, adopt/forget, orderings since 10.1.84**; switching reads (LAG/stacks) 10.3.58. Many TCT consoles are behind — per-console `FIRMWARE_UNSUPPORTED` is an expected common case, and `unifi_probe_consoles` / `scripts/probe-unifi-consoles.ts` produce the remediation list.
- **NOT in the official Integration API — do not fake or fall back to the internal `/api/s/{site}` API**: locate/LED, client block/unblock/reconnect, port forwards, static routes, site health/ISP metrics, events/alarms, port profiles, gateway settings, firmware triggers. (ISP metrics exist in the separate cloud Site Manager API.) Full omitted-with-reason list: `docs/unifi-site-tools.md`.
- **Cloud Connector Proxy limits (documented)**: 100 requests/min PER CONSOLE (429 + `Retry-After` — the client honors short waits once, surfaces the rest), 25 s proxied-request timeout (408 → typed `TIMEOUT`), 10 MB response cap, ~800 ms added latency. List endpoints paginate `offset`/`limit` (max 200) with the `{offset,limit,count,totalCount,data}` envelope.
- **Integration API PUT replaces the whole object** — updates must GET→merge→PUT (same reason IT Glue writes are GET-merge-PATCH). `unifi-staged-writes.ts` does this; never PUT only the changed fields.
- **WLAN objects carry secrets** (`passphrase`, PPSK `presharedKeys`, RADIUS secrets). Every read and every stored snapshot goes through `redactSecrets()`. WLAN **create** and passphrase changes are deliberately not exposed — the API requires `securityConfiguration` on create and the staged-write audit row must never persist a secret. **SSID→VLAN binding is the `network` field** (`{type:"NATIVE"}` or `{type:"SPECIFIC",networkId}`) — added to the `unifi_wlan` allowlist for segmentation. `uapsdEnabled` was **removed** from that allowlist: it is not in the current WiFi-broadcast schema (a silent drift from an older version; PUTting it 400s).
- **Network create on 10.4.x requires more than the old allowlist exposed (2026-07-20, live-confirmed on Tri County Refrigeration, Network app 10.4.57)**: a GATEWAY network create now 400s with *"cellularBackupEnabled/ipv4Configuration/isolationEnabled/internetAccessEnabled must not be null"* unless all four are sent. `ipv4Configuration` (subnet/DHCP object) was not even in the allowlist, so the connector could never set a VLAN's subnet or DHCP scope. Fix: widened the `unifi_network` allowlist to the real API fields and added `normalizeUnifiChanges()` (in `staged-writes-core.ts`) — a pure pre-validation payload builder that expands convenience inputs (`subnet` CIDR, `dhcpMode`/`dhcpStart`/`dhcpStop`/`dhcpLeaseTimeSeconds`/`dhcpDnsServers`/`dhcpDomainName`/`dhcpRelayServers`) into a full `ipv4Configuration` and defaults the flags (internetAccessEnabled=true, isolationEnabled=false, cellularBackupEnabled=false, management=GATEWAY, enabled=true), so `name`+`vlanId` alone still creates a working VLAN (subnet derived `192.168.<vlanId>.1/24` for vlanId 2-254). Convenience keys are consumed there and never sent/stored — the gate still validates/diffs/writes only real allowlisted API fields, and update stays GET→merge→PUT. **`ipv4Configuration` required = `autoScaleEnabled`+`hostIpAddress`+`prefixLength`(8-30); SERVER `dhcpConfiguration` = `mode:"SERVER"`+`ipAddressRange{start,stop}`+`leaseTimeSeconds`+`pingConflictDetectionEnabled`.** Ubiquiti has NOT published 10.4.x docs — v10.3.58 is the newest published spec and carries the identical required set; the live 10.4.57 console confirms it. Firewall zone/policy and ACL create schemas were re-checked at v10.3.58 and had NOT drifted.
- **Drift check must compare snapshots order-INSENSITIVELY once a nested object is in the allowlist (2026-07-20, live-confirmed on TCR).** `detectDrift` compares each snapshot field with `JSON.stringify` — order-sensitive. The staged `before` is persisted in a **JSONB column, and Postgres JSONB does not preserve object key order**, so a nested-object field (a UniFi network's `ipv4Configuration`) comes back in a different key order than the live API returns it, and every update/delete of a gateway network false-drifted (`Live UniFi record changed since staging (fields: ipv4Configuration)`) even though nothing changed. Scalars survive the round-trip, so this stayed hidden until `ipv4Configuration` (the first nested object) joined the allowlist. Fix: `canonicalizeKeys()` (deep key-sort, array order preserved) applied to BOTH sides in `unifi-staged-writes.ts` right before `detectDrift` — `detectDrift` itself is unchanged, and real value changes are still caught (verified: /24→/25 still drifts). Evidence that nailed it: two back-to-back delete stagings captured byte-identical `before`, so the record was stable read-to-read — only the JSONB→API key-order mismatch differed. Any future connector area that snapshots a nested object inherits this defense automatically.
- **UniFi writes are structurally gated**: single console/site/target per schema (no arrays — unit-tested), kill switch `CONNECTOR_UNIFI_WRITES_ENABLED` (independent of the Autotask one), tier 1 attributed via structured logs, tier 2 through the same `ConnectorStagedWrite` human-approval gate (UniFi rows use `targetSystem='unifi'`, string targets encoded in `entityPath` as `consoles/{consoleId}/sites/...` because `entityId` is Int; `unifi_execute_staged_write` / `autotask_execute_staged_write` each refuse the other's rows BEFORE the single-use claim so an approval is never burned by the wrong tool).
- **Network deletes**: stage WITHOUT the API's `force` flag; staging auto-reads `/networks/{id}/references` and stamps a warning on the approval card when the network is still referenced.
- **Reading the official spec**: developer.ui.com is a JS app, but every docs page embeds the complete OpenAPI document in its RSC payload (`"fullSpec"`), version-pinned per Network release — extract that instead of scraping rendered pages. Same trick works for **Protect** (`/protect/v7.1.87/*`) and **Site Manager** (`/site-manager/v1.0.0/*`). Two extraction gotchas: the payload continues past the spec object, so `json.loads()` dies with *"Extra data"* — use `JSONDecoder().raw_decode()`; and the doc index redirects to the newest version, so `https://developer.ui.com/protect/` is how you learn which Protect version is current.
- **help.ui.com returns 403 to non-browser clients** (any `curl`/WebFetch of `/hc/en-us/articles/...`, browser UA or not). It runs Zendesk, so read articles as JSON instead: `https://help.ui.com/api/v2/help_center/en-us/articles/{id}.json` (200, includes `title`/`body`/`updated_at`), and search with `https://help.ui.com/api/v2/help_center/articles/search.json?query=...`. **community.ui.com has no such escape hatch** — it is a client-rendered SPA that returns a 1,842-byte JS shell to everything; don't burn time on it.

## Datto RMM Integration — Key Knowledge

Single client: `src/lib/datto-rmm.ts` (`DattoRmmClient` — OAuth2 *password* grant at `{DATTO_RMM_API_URL}/auth/oauth/token` with Basic `public-client:public`, username = `DATTO_RMM_API_KEY`, password = `DATTO_RMM_API_SECRET`; token cached in-instance, 100 h lifetime, 401 auto-refresh). Consumers: SOC enrichment, TBR/executive/annual reports, compliance collectors, the every-30-min `datto-device-sync` cron, and the MCP connector's read-only reporting tools (`src/lib/mcp-datto-rmm-tools.ts`, reference: `docs/reference/DATTO_RMM_CONNECTOR_TOOLS.md`).

- **THE `page` PARAMETER IS 0-INDEXED (2026-07-18, live-confirmed)**: `page=1` returns the SECOND page. Confirmed against production: `/v2/account/sites?page=1` returned 0 rows while `pageDetails.totalCount` reported 213 sites; `/v2/account/alerts/open?page=1` returned 0 while the console showed 13 open (incl. a High). Every paged loop must START AT `page=0`. This was ALSO the real cause of the old "account devices returns 5 of hundreds" mystery (261 devices − 250 on page 0 = the ~few stragglers page=1 returned): the original client started all sweeps at `page=1`, so the device-sync cron missed the first 250 devices and the executive summary read 0 open alerts. Fixed in `datto-rmm.ts` (all four loops) + `mcp-datto-rmm-tools.ts` (`pagedGet`, tool `page` params are 0-based); the unit-test mock now serves rows ONLY on page 0 so a page-1 regression fails the suite.
- **Site UID vs numeric id** (also under SOC): sites and devices have BOTH a numeric `id` and a UUID `uid`. Site-scoped endpoints (`/v2/site/{uid}/…`) take the **UID**; `/v2/device/id/{id}` exists for the numeric device id. **Activity-log rows reference the numeric ids** (`site.id`, `deviceId`), not UIDs.
- **Account-wide vs per-site device listing**: `/v2/account/devices` supports server-side LIKE filters (`hostname`, `deviceType`, `operatingSystem`, `siteName`, `filterId` — filterId *exclusively* determines results) and, now that pagination starts at page 0, returns the full fleet. Per-site `/v2/site/{uid}/devices` remains the habit for per-customer inventory (matches how mappings scope SOC lookups). The old "returns only a subset (5 of hundreds)" note was the 0-index pagination bug above, not an API limitation.
- **The live OpenAPI spec is fetchable without auth**: `GET {API URL}/api/v3/api-docs/Datto-RMM` (behind the Swagger UI at `{API URL}/api/swagger-ui/index.html`). 39 GET endpoints as of 2026-07-18. Re-verify there before adding endpoints; two spec surprises found this way: `/v2/device/{uid}/patch` (used by the old `getDevicePatch()` diagnostic) is NOT in the spec (patch data is `patchManagement` on the Device object), and alerts have **no `alertType` field** — the monitor type is `alertContext['@class']` (e.g. `perf_disk_usage_ctx`). The pre-existing `mapAlert()` in `datto-rmm.ts` reads top-level `hostname`/`siteUid`/`deviceUid` that per spec live under `alertSourceInfo` — the connector tools read the nested shape; if SOC alert paths ever look empty, check that mapping.
- **The API returns console deep links — never construct them**: `portalUrl` on Site/Device/DeviceAudit/ESXi/Printer audits (+ `webRemoteUrl` on devices). No URL pattern for alerts is documented anywhere (help pages + Integrations Whitepaper checked 2026-07-18); the connector tools resolve alert-row site/device links from cached sites/site-devices sweeps instead of guessing a pattern.
- **Secrets in read responses**: `Site.proxySettings` / site settings include a proxy `password` field — redact before returning anywhere; account/site variables carry `masked` — force `[MASKED]` values on output regardless of what the API returned.
- **Rate limits**: 600 reads/60 s sliding window (100/60 s writes), 1 s delay injected at 90% quota, 429 on breach, persistent breach = temporary IP block (wait 5 min). `GET /v2/system/request_rate` reports current usage. Connector tools wrap GETs in `withRetry` (429/5xx/timeout transient, 400/404 immediate).
- **Pagination**: `page`/`max` (250 cap), `pageDetails.nextPageUrl` presence = more pages. `/v2/activity-logs` alone is cursor-based (`searchAfter` + `page=next|previous`; default window = last 15 min, so always pass `from`/`until` for reports) and takes CSV multi-value filters.
- **The MCP tool surface is GET-only by construction**: tools can only call `DattoRmmClient.getV2()` (no method/body parameter, `/api/v2/` paths only) — enforced by unit test (`mcp-datto-rmm-tools.test.ts` proxies the client and fails on any other method). The API's write surface (quickjob, device move, UDF/warranty set, alert resolve, site/variable CRUD, `resetApiKeys`) is deliberately unimplemented; if ever wanted it goes through the staged human-approval gate like Autotask/UniFi config writes.

## DNSFilter Integration — Key Knowledge

Single client: `src/lib/dnsfilter.ts` (`DnsFilterClient`, `Authorization: Token <token>`). Other query_logs callers: SOC enrichment (`fetchDns`), AI-discovery prefill.

- **query_logs `from`/`to` MUST be DATE-ONLY `YYYY-MM-DD` for historical windows (2026-07-19, live-verified)**: a full-ISO `from` more than 9 days before now is rejected with HTTP 400 *"Time period (from now) is greater than 9 days"*; the SAME window as date-only returns 200. This was the root cause of DNSFilter "returning nothing" in annual/TBR reports — every ~30-day pull 400'd and was caught into zeros. Full-ISO is accepted (and keeps hour precision) only when `from` is within 9 days of now — the SOC enrichment uses precise timestamps for fresh alert windows and falls back to date-only + client-side time filtering for older re-triage.
- **`/v1/traffic_reports/query_logs` EXISTS and is the blocked-traffic source.** Do not "simplify" to `top_categories`/`top_domains`: both silently IGNORE `result=blocked` and return TOTAL traffic. Blocked breakdowns are aggregated client-side from query_logs rows: blocked total = `data.page.total` with `result=blocked`; categories from each row's `categories_names[]`; domains from `domain` (fallback `fqdn`).
- **Paginate query_logs rows** with `page[size]` + `page[number]` (1-based; first page may omit `page[number]`). One page truncates category/domain counts. `getTrafficReport` pages to `data.page.total` with a 50×100-row cap and flags `breakdown_partial` (surfaced in the summary `note`) instead of silently truncating.

## Reporting — First Response & First Touch Definitions (2026-07-21)

The regenerated Tri-Bros June review still showed a fabricated **0m average first response**, **100% response SLA**, and **0% first-touch resolution** even after automated tickets were excluded — because the remaining HUMAN tickets were mis-measured. Three field realities, all live-confirmed, and the fixes (shared helpers in `src/lib/reporting/lifecycle.ts`, locked by `first-response.test.ts`):

- **The first note is usually the INTAKE record, not a response.** On a phone/portal/onsite ticket the tech logs the call they are already on (or an integration posts the request summary) AT creation. Autotask's own `firstResponseDateTime` equals `createDate` on such tickets (14/14 Tri-Bros June human tickets). The old code read the first tech note's timestamp → 0-minute delta → scored as instant response + 100% SLA. **Fix:** `resolveFirstResponse()` — a ticket **opened by human staff** (`creatorResourceId` is a real tech) is `answeredAtIntake` (no queue wait to measure: null, reported separately as "answered live at intake", NEVER 0), and only genuine human notes/time-entries AFTER creation by non-API accounts count as a response. FRT averages/medians and the response-SLA denominator both exclude intake-answered tickets, so the fake 0m/100% disappears (null = not measured, not a breach).
- **First-touch resolution ≠ "≤1 note".** An intake note plus a resolution note by the same tech is ONE human touch, but the old rule (`techNotes.length <= 1`) failed it → fabricated 0% FTR. **Fix:** `countDistinctHumanParticipants()` — FTR = resolved by a single human owner with no reopens, counting DISTINCT human resource ids across notes + time entries (API/system accounts excluded via `isApiOrSystemUser`).
- **API/system accounts are never human responders.** First-response and first-touch both filter note/time-entry authors through the same `isApiOrSystemUser` set the technician reports use (`getHumanResourceIds()`), so SaaS Alerts / integration / dashboard-user activity can't masquerade as a human touch.
- **Median must come from the same population as its average.** The old business-review median resolution was computed from `lifecycles` (ALL tickets active in the period) while the average came from `closedInPeriod` — two different populations shown side by side (PDF: avg 5.8d, median 5.5d that don't correspond). Same for the priority breakdown: counts over created-in-period, resolution avg over all-active. **Fix:** both the resolution median and the per-priority resolution average are computed over the SAME cohort as their neighboring count (created-in-period for the priority table; closed-in-period for the headline avg/median).
- **Small-sample outlier framing.** A 2-ticket multi-week outlier in a 10-ticket month produced "avg resolution +459.7%" — a real number but misleading. When the median is < half the average, the customer narrative now leads with the median ("most requests resolved in ~Xh; the higher average reflects a few complex items"), not the alarming percentage. This is presentation only — the numbers are unchanged and honest.

## Reporting — SLA is Autotask's own per-contract result, Fully-Managed only (2026-07-21)

Owner-directed model, replacing the reporting-engine's SLA recomputation:

- **SLA compliance now comes from Autotask's OWN SLA determination**, not our recompute. We sync Autotask's native SLA event datetimes onto `tickets` (`firstResponseDateTime`/`firstResponseDueDateTime`, `resolutionPlanDateTime`/`…DueDateTime`, `resolvedDateTime`/`…DueDateTime`, `slaHasBeenMet`) and the lifecycle engine reads the verdict straight off them (`metByDue`: met = actual ≤ due). The old `reporting_targets` business-hours recompute in `computeTicketLifecycleInMemory` is gone — it drifted from each customer's actual contracted SLA (it's what produced "Resolution SLA 50%" on Tri-Bros when Autotask's own answer was 4/6 met). Autotask already applies the right per-contract targets, business hours, and pause logic; don't re-derive it.
- **SLA is reported ONLY for the "TCT – Fully Managed IT Services" agreement** (SLA id 2, live-confirmed; resolved via `getFullyManagedSlaId()` / `isFullyManagedSla()` in `sla-config.ts`, name-refreshed from the live SLA picklist during sync). `isSlaReportableTicket()` is the single gate: Fully Managed SLA **AND** human/user-created **AND** not an automated alert queue. Everything else → null SLA verdict = "not measured". This mirrors the ops SLA widgets (`Service Level Agreement = TCT – Fully Managed IT Services`, `Queue != Monitoring Alert`).
- **The three SLAs (live):** id 1 "Standard SLA" (99% goals), id 2 "TCT – Fully Managed IT Services" (95% goals — the reported one), id 3 "No SLA" (0 goals). All automated monitoring tickets are on **No SLA** — confirmed on Tri-Bros June (33/33). "No SLA"/null-SLA tickets never enter an SLA denominator.
- **Business review scope:** `servicePerformance.slaApplicable` = does the customer have any Fully-Managed user ticket this period. When false, the SLA cards + narrative are **omitted entirely** (not shown as "—") — SLA isn't part of that customer's plan. FRT/resolution/FTR/reopen still show for everyone.
- **`serviceLevelAgreementHasBeenMet` = null means the SLA roll-up isn't finalized** (ticket still in flight / no resolved event), NOT a breach. Never count null as a miss.
- **CONFIG, not code — contract category ↔ SLA mismatches:** a "Managed Service – Platinum/…" contract should carry the Fully Managed SLA. AllSpec Finishing was Platinum but on **Standard SLA** — such a customer gets NO SLA section until the contract's SLA is corrected in Autotask. The report faithfully reflects the attached SLA; fixing the mismatch is an Autotask config change (audit via `autotask_list_contracts` → compare `contractCategoryName` to `slaName`).
- **Operator steps after deploy** (native SLA fields are new columns, empty until re-synced): POST `/api/migrations/run`, then re-sync tickets (so historical rows populate the native SLA datetimes), then re-run `compute_lifecycle`. Until then, SLA reads null → "not measured" (honest), never a fabricated number.
- **`compute_lifecycle` is resumable across its 50s time budget, and a big backfill needs several runs (2026-07-21b).** A forced full ticket re-sync stamps `autotaskLastSync = now` on thousands of tickets at once; `computeLifecycle` can only process ~1400/run before the time guard stops it. The job query filters `autotaskLastSync > lastSuccessfulRun` — and a time-budget stop is deliberately **NOT** counted as a successful/advancing run (a timeout finishes `failed`, non-advancing; `getLastSuccessfulRun` counts both `success` and `partial`, so neither may be used for a timeout or the un-processed tail gets skipped). Progress instead comes from a **checkpoint filter**: candidates are dropped when their `ticket_lifecycle.computedAt >= ticket.autotaskLastSync`, so each run's committed rows fall out of the next run's set. Net: run `compute_lifecycle` repeatedly (the API response / job meta shows `remaining`) until `remaining` hits 0 and it flips to `success` (that final clean pass advances `lastRun`). Before this fix a partial run re-queried the same set in the same order and redid the same first chunk forever — a large backfill (or the scheduled cron) would wedge. **Scope the re-sync to one company (`?company=`) when you only need that customer refreshed — then it's a single sub-second `compute_lifecycle` pass.**

## Thread Integration (customer chat) — Key Knowledge

- **Thread's Automation URL cannot send auth headers or signatures** (verified against https://docs.getthread.com/article/7vxm10v3zj-magic-agents-automation-url) — it POSTs a bare JSON body `{ intent_name, intent_fields, meta_data }`. The original `x-thread-signature` HMAC design in this repo was an internal invention Thread can never satisfy. Auth is therefore a URL key: `?key=<THREAD_AUTOMATION_KEY>` on `/api/integrations/thread/webhook`, checked by `checkAutomationKey()` in `src/lib/api-auth.ts` (timing-safe, **fail-closed: unset env var = every request 401s**, never an unsigned path). The full URL including the key is the credential — it is pasted into each Magic Intent's Automation URL field in Thread and must never be committed or logged.
- **One Automation URL per intent, with `&type=onboarding` / `&type=offboarding`** — that query param is the deterministic form-type signal; `intent_name` keywords are only a fallback, and an undeterminable type is a 400 (fix the URL in Thread, don't guess).
- **`meta_data.company_id` is the Autotask company ID** and is the PRIMARY company resolver (`resolveFormCompany()` in `src/lib/form-links.ts`: autotaskCompanyId → slug exact → displayName exact → active-contact email domain → fuzzy name LAST). Fuzzy matching NEVER runs when an exact identifier was supplied, and ambiguous domain/fuzzy matches (2+ companies) resolve to nothing — unresolved = 404 `{ error: 'not_configured' }`. If Thread 404s for a real customer, the fix is setting `companies."autotaskCompanyId"` (or running the Autotask sync), not loosening the matcher.
- **Response contract**: Thread relays `message` verbatim to the customer and expects exactly `200 { "success": 200, "message": "<text>" }` — the form link must be INSIDE the message text; separate `link` fields are not relayed. Locked by `src/app/api/integrations/thread/webhook/route.test.ts`.
- **Single-use + chat↔ticket linkage**: `POST /api/forms/links/[token]/used` (called by FormLinkPortal after submit) stamps `form_links.used_at` + `form_links.request_id`; Thread links also carry `form_links.source_meta` (the Automation URL `meta_data` — `ticketId` is the Thread chat-ticket ID). Join chain for the future chat-ticket/Autotask-ticket merge: `form_links.token → request_id → hr_requests.autotask_ticket_id/number`, with the Thread ticket id in `source_meta`. The linkage is only as reliable as the client-side `/used` call — if it must become server-authoritative, thread the token through `/api/hr/submit` instead of adding a second marking path.
- **New `form_links` columns (`request_id`, `source_meta`) are raw-pg** — canonical DDL in `/api/migrations/question-engine` (GET with `?secret=MIGRATION_SECRET`); the admin forms-schemas route and the writers (`createFormLink`/`ensureFormLinkColumns`) also apply idempotent `ADD COLUMN IF NOT EXISTS` backfills, so no deploy-order window. Programmatic link minting (`POST /api/forms/links`) accepts the same key via `x-automation-key` header and now resolves companies with the same helper.
- **`form_links` UUID columns vs TEXT ids (live-confirmed 2026-07-10)**: `form_links.company_id`/`request_id` are `UUID`, but `companies.id` and `hr_requests.id` are `TEXT` (Prisma String @id). Any JOIN or equality between them needs an explicit cast (`c.id = fl.company_id::text`) or Postgres fails at parse time with `operator does not exist: text = uuid` (42883) — this broke BOTH token-validation paths in production from day one (the original code shipped without the cast and the feature was never exercised, so it never surfaced; no e2e spec covers these routes). Untyped INSERT params coerce fine, which is why link creation worked while validation didn't. Don't "fix" this by ALTERing column types on live tables — cast in queries.

## HR Onboarding/Offboarding Automation (`/api/hr/process`)

- **Every requested action must appear in the ticket record — reconcile, don't accumulate.** The 2026-07-05 incident (ticket T20260704.0004): "convert to shared mailbox" was requested, but the pipeline had no automated step for it and the only logging path was gated on `shared_mailbox_access` being a non-empty array — the action was neither executed nor mentioned anywhere. Fix: `src/lib/hr/offboarding-actions.ts` derives the full requested-action list from the answers and reconciles it against executed/failed step keys; every action renders in PROVISIONING RESULTS as `[DONE]/[FAILED]/[MANUAL]/[QUEUED]/[NOT RUN]`, and un-run automated steps force a manual step + escalation. **When adding a new offboarding capability or form field, add it to `deriveRequestedOffboardingActions()` — never only to the pipeline.**
- **Microsoft Graph cannot convert a mailbox to shared, set mailbox forwarding (`Set-Mailbox`-style), or grant mailbox Full Access** — those are Exchange admin center / Exchange Online PowerShell operations. As of 2026-07-05 the conversion + delegation ARE automated for **enabled tenants** via the Azure Automation Exchange runner (`src/lib/exchange-online.ts`; setup: `docs/runbooks/EXO_AUTOMATION_ENABLEMENT.md`); tenants without enablement keep the explicit `[MANUAL]` outcome + NEXT STEPS instruction with the reason attached. Forwarding is still `[MANUAL]` (phase 2).
- **keep_accessible NEVER removes the license inline** — the mailbox must be licensed at the moment it is converted to shared (Microsoft-documented order). Enabled tenants: the callback removes licenses AFTER the verified conversion, and only when the runner judged it safe (<50 GB, no litigation/in-place holds, no active archive — otherwise `[MANUAL]` license-retained note). Manual path: the NEXT STEPS instruction says convert first, THEN remove the license. Do not "fix" the pipeline back to inline removal.
- **License-removal ordering is now an explicit, guarded invariant (2026-07-22).** The order was previously only implicit call-site order, which is how it regressed — reported on Tri-Bros Transportation, originally Dan Brown Construction / Michael Beach (license pulled before the mailbox was converted → conversion + access grants failed on the unlicensed account). The intended sequence is the single-source-of-truth constant `OFFBOARDING_STEP_ORDER` in `src/lib/hr/offboarding-actions.ts` with `remove_licenses` AFTER `convert_shared_mailbox`; `deriveRequestedOffboardingActions()` emits its plan in that order and self-checks via `assertLicenseRemovalAfterMailboxConversion()` (which throws if license removal precedes the conversion). `/api/hr/process` carries the same rule as a runtime tripwire — it fails the request if `remove_licenses` ran inline for a keep_accessible offboarding — and `offboarding-actions.test.ts` locks the order. Do not reorder those two keys or make the ordering implicit again. NOTE: all offboarding triggers (portal submit, Thread webhook → form link → submit, scheduled-offboards cron) converge on `/api/hr/process` — there is ONE execution engine, so the fix lives in one place.
- **Async Exchange jobs are verified, never assumed.** A 202 from the Azure Automation webhook = `[QUEUED]`, nothing more. The runbook re-reads Exchange state (`RecipientTypeDetails`, `Get-MailboxPermission`/`Get-RecipientPermission`) and the callback route additionally asserts observed == requested (`evaluateExchangeJobResult`) before any `[DONE]` — a runner that claims success without matching observed state is finalized as FAILED. Lost callbacks: `/api/cron/exchange-jobs-reconcile` times jobs out after 45 min into `[FAILED]` + manual instructions + priority escalation. Never mark a step done from a dispatch acknowledgment (that is exactly how T20260704.0004-class lies happen).
- **Exchange RBAC scoping**: "RBAC for Applications in Exchange Online" (Application Mail.Read etc.) covers **Graph/EWS only — NOT PowerShell cmdlets**. The least-privilege path for app-only PowerShell is a custom role group holding the `Mail Recipients` role with the app's Exchange service principal as member (app-only-auth doc Option 2). `Enable-TctExchangeTenant.ps1` verifies per-tenant that every runbook cmdlet is actually granted by that role. Role-group changes hit an up-to-2h RBAC cache — a probe failing right after enablement is usually just that.
- **EXO module in Azure Automation**: PowerShell 7.4 runtime (7.1/7.2 retired); ExchangeOnlineManagement 3.x requires PowerShellGet + PackageManagement uploaded to the same runtime environment or jobs fail at import. `WebhookData` can arrive as a JSON string in PS7 runbooks — the runbook normalizes before parsing.
- **Form schema values drift across generations** — three schema generations exist (seed SQL, question-engine seed, `/api/forms/config` migrations): e.g. delete-after-hold is `delete_after_backup` vs `delete_after_30` vs `delete_after_30_days`; devices are `wipe_remote`/`remote_wipe`/`wipe`. The processor matched only one value and 30-day deletion scheduling silently never fired for the live schema. Match ALL generations (see `DELETE_AFTER_HOLD_VALUES`) and keep `VALUE_LABELS` in sync when adding options.
- **Autotask notes/descriptions mangle non-Windows-1252 glyphs** — `✓`, `⊘`, `→`, `⚠` render as `?` in ticket notes (confirmed live). Use ASCII markers (`[OK]`, `[SKIPPED]`, `->`); `—` and `•` are CP1252-safe and fine.
- **`automation_mappings` (question-engine) is seed-only** — nothing reads it at execution time; the process route is a hardcoded pipeline. Its `convert_to_shared`/`setMailForwarding` graph methods were never implemented (and can't be, per the Graph limitation above). Don't treat those mappings as evidence a capability exists.
- The old Microsoft Forms onboarding/offboarding forms are retired; IT Glue SOPs (docs 16573760, 14639952, 20377379 in org 6942365) were rewritten 2026-07-05 to portal-first intake + the PROVISIONING RESULTS checklist workflow.
- **Two sessions built the Exchange automation in parallel on 2026-07-05** — a lighter variant (`exo_jobs` table, `/api/webhooks/exo-jobs`, `EXO_ENABLED_TENANTS` env allowlist, `scripts/exo/`, PS 7.2 runbook, no lost-callback cron) briefly landed on main (commit `b8d5740a`) and was superseded by the fuller implementation described above (registry + probe, reconcile cron, automated post-verification license removal, PS 7.4, `Mail Recipients` scoping). If an empty `exo_jobs` table exists in prod from a migrations run during that window, it is orphaned and harmless — do not resurrect the variant's paths.

**CFO gotchas:**

Must be a 32-byte base64 string (~44 chars), set in **Production** scope, and the app **redeployed** (env changes need a fresh deploy). Real accrual profit = the QuickBooks panel. Don't conflate. Vendor-level expense detail is NOT in Sequence (most spend is on Amex, paid as one lump) — it lives in QuickBooks.
- **Demo mode** (`demo.ts`, via existing AdminHeader toggle): masks every name through `useDemoMode().company()` and scales every cents value by ONE consistent factor (`num(_, 'cfo-scale')`) so ratios/runway/payoff math stay correct.
- **Scheduled outflows** (Settings): user-entered known upcoming payments override the baseline in the forecast + "covers payroll" card. **Live QB overrides stored QB/AR snapshots** once connected.
- `cfo_settings` is raw-pg/self-healing (`ensureCfoTables`), NOT Prisma — like reporting/SOC.
- **Hiring calculator (`src/lib/cfo/hiring.ts`) is a 1:1 port of the owner's "TCT New Hire Breakeven Calculator" workbook (July 2026)** — 3 hire types (US W-2 / US 1099 / PH contractor) × 3 tiers, NY employer taxes with wage-base caps (FUTA $7k, SUTA+RSF $17.6k, SS $184.5k — `MIN(annual base, cap) × rate`), workers' comp class 5191 (1.22%; clerical 8810 would be 0.10%), itemized tooling/equipment/onboarding detail. Cost applicability mirrors the workbook: taxes/WC/health/equipment/onboarding = W-2 only; 13th-month/payment-fee/paid-holidays = PH only; per-seat tooling = every hire type. NY DBL/PFL is employee-paid (reimbursed to TCT) — deliberately NOT an employer cost line. `src/lib/cfo/hiring.test.ts` asserts parity with the workbook's computed cells — don't change the math without reconciling against the workbook. Assumptions persist in `cfo_settings` key `hiring_assumptions` guarded by `isHiringAssumptions()` (`version: 2`); pre-v2 saved payloads fail the guard on load and the defaults win (no data migration needed).
- **Spend insight comes from QuickBooks, not Sequence**: vendor/category spend-over-time + month-over-month anomalies (`d.qbSpend`) are built from month-summarized QBO reports (`getProfitAndLossByMonth` = category×month, `getVendorExpensesByMonth` = vendor×month) parsed by `parseSpendSeries` and flagged by `detectSpendAnomalies`. Live-only (null when QB disconnected) over the last 12 **complete** months. **If the vendor section/anomalies are missing, `VendorExpenses` likely didn't honor `summarize_column_by=Month`** (returns a single Total col → no months parsed → graceful skip); fall back to per-month `ProfitAndLossDetail`/`TransactionListByVendor`. Don't confuse with `perPodAnomalies` (Sequence pod, weekly).

## Sales Calculator — `/admin/sales-calculator`

- **Effective pricing = `src/config/sales-calculator/pricing.json` (defaults) + DB overrides.** Overrides live in raw-pg `sales_calc_pricing_overrides` as a flat path→number map (e.g. `{"packages.basic.perUser.price": 40}`), **append-only** — every save inserts a new row (history = audit trail); the latest row wins. Edited at `/admin/sales-calculator/pricing` (any staff can view; saving requires the `system_settings` permission). The overrides API validates every path against pricing.json — overrides can only change EXISTING numeric leaves, never add keys or change shape.
- **New deploys of the overrides feature need the migration POSTed once** (`POST /api/migrations/run` with `MIGRATION_SECRET`) — until then the calculator runs on config defaults and the editor shows a run-migrations banner with saving disabled. The GET endpoint treats Postgres error `42P01` (undefined table) as "no overrides yet", NOT as a 500.
- **The calculator and the authenticated e2e spec BOTH layer live overrides before computing quotes** (`applyPricingOverrides()` from `src/lib/sales-calculator/config.ts`). If you compute expected totals in a test from pricing.json alone, it will break as soon as an admin overrides a price — fetch `/api/admin/sales-calculator/pricing` and apply first (see `tests/e2e/authenticated-sales-calculator.spec.ts`).
- **Service inclusion is tri-state**: `include` values in `services.json` are `true` (included), `"billable"` (available but billed hourly / T&M — the Comprehensive-vs-Complete support-model difference), or `false` (not available). NEVER test inclusion with truthiness — `"billable"` is truthy but is NOT included; use `serviceInclusionState()` from config.ts. Billable services are excluded from bundle revenue allocation and from `includedServices` (they get their own `billableServices` list on the quote).
- **Per-package support model** (reactive vs proactive) lives in `packages.json` → `supportModel.{label,detail}` and renders on the Comparison "Support Model" row, the Catalog banner, and the Recommendation card. It is copy, not logic — edit the JSON.
- **"Shared" service state is DISPLAY ONLY.** `packages.json` → `<package>.sharedServices` (today: Ally/comanaged lists `helpdesk`, `unlimitedSupport`, `vendorMgmt`) makes those cells render a 👥 "Shared — delivered jointly with your internal IT" icon on the Comparison matrix, Catalog and comparison PDFs via `serviceDisplayState()` (config.ts). The MONEY treatment still comes from `serviceInclusionState()` — helpdesk/remote-support stay hourly-billable, vendor management stays included in the Ally bundle. calc.ts must never read `serviceDisplayState`; `src/lib/sales-calculator/shared-display.test.ts` locks both sides.
- **Saved quotes** live in raw-pg **`sales_calc_saved_quotes`** (CRUD at `/api/admin/sales-calculator/quotes`, any staff session; soft delete only). A quote stores the discovery **inputs** (+ a small `summary` snapshot for the browse list) — **never prices**: loading reprices at current pricing.json + live overrides. Old payloads are absorbed by `normalizeSavedInput()` (deep-merge over `defaultInput()`; unknown keys dropped, type mismatches → defaults) — bump `SAVED_QUOTE_INPUT_VERSION` only for changes that merge can't absorb. **New table = POST `/api/migrations/run` once after deploy**; until then the API returns `tableMissing` and the UI shows the run-migrations banner with saving disabled (Postgres `42P01` handled like the pricing overrides table). The authenticated e2e spec writes one `E2E Saved Quote <ts>` row per run and soft-deletes it — harmless residue rows in the table are expected.
- **Read-only MCP connector tools expose this pricing (2026-07-28).** `sales_pricing_catalog` (the whole model: every tier by its verbatim name, per-unit cost + sell rates by unit type, add-ons, M365 requirements/rates flagged billed-separately, and the calculation rules) and `sales_pricing_quote` (the calculator itself — discovery inputs in, computed monthly/annual per tier out), both in `src/lib/mcp-sales-pricing-tools.ts`. Built because `/admin/sales-calculator*` is behind staff auth AND returns `ROBOTS_DISALLOWED` to `web_fetch`, so pricing was being pasted into chat by hand. **Read-only by construction** — no write/stage/execute verb exists and rate edits still require a staff session with `system_settings` at the pricing editor, which an MCP bearer token cannot reach. Responses DO carry vendor costs and margins: every response self-labels `internalOnly`; never paste raw figures into customer-facing copy.
- **Server-side quoting MUST go through `withEffectivePricing()`** (`src/lib/sales-calculator/pricing-source.ts`). `applyPricingOverrides()` **mutates the shared `pricingConfig` module singleton** — harmless in the browser (one user per tab) but a cross-request data bug on the server, where one lambda instance serves many callers and a removed override would otherwise persist as a stale value. The helper resets to a pristine snapshot → applies overrides → runs a **synchronous** callback → resets in a `finally`. Node runs a synchronous block to completion without interleaving another request, which is what makes the mutation window atomic: **never `await` inside that callback**, or one customer's overrides can price another customer's quote. `pricingSingletonIsPristine()` locks it in `mcp-sales-pricing-tools.test.ts`.
- **`pricing-source.ts` is the ONE reader of effective pricing** (defaults + latest overrides row) and is **SERVER-ONLY** — it imports the raw pg pool, so importing it from a `'use client'` component puts `pg` in the browser bundle. The pricing GET route uses it too; don't add a second overrides query.
- **Hand-derived tier totals always come out SHORT — don't "correct" the calculator to match them.** Reverse-engineering a generated comparison from per-user/per-device rates alone fails because three lines are easy to miss: the per-company **Business Line** charge (`max($250 floor, 2 × monthly company cost)`, on Comprehensive/Complete/Ally only), the per-**internal-IT-admin seat** ($150 — `perComanagedAdmin` on Ally, `comanagedToolAccess` on a fully-managed tier), and **servers** (the only rate that differs between the Comprehensive/Complete pair at $115 and everything else at $100). Worked example: the Wilmar + EZ Red comparison (Manufacturing, 3 locations, 133 users, 132 PCs → Basic $10,525 / Standard $10,675 / Comprehensive $16,995 / Complete $21,940 / Ally $12,250) is NOT reproducible from those four inputs — it also carried **6 servers** and **$350/mo of package-independent add-on lines**. Locked in `mcp-sales-pricing-tools.test.ts`. There are **no** volume, term-length, industry/vertical or compliance modifiers anywhere in the model — if a total doesn't reconcile, a quantity is missing, not a hidden multiplier.
- **The calculator's `marginPct` is TOOLING-ONLY — it is not profit (2026-07-28).** `pricing.json` unit *costs* are vendor/tooling costs and nothing else, so the 85-93% margins the engine reports exclude every hour of delivery labor. The labor side lives in `src/config/sales-calculator/labor.json` + pure `src/lib/sales-calculator/labor.ts`, which composes on top of a finished `PackageQuote` — **`calc.ts` is deliberately untouched** so the spreadsheet parity holds (`labor.test.ts` asserts quoted prices stay byte-identical, including the Wilmar comparison). Quote `trueMargin.contributionMarginPct`, never `marginPct`.
- **Quote CONTRIBUTION, never fully-absorbed cost.** Allocating the fixed pool per endpoint gives a cost-to-serve that FALLS as the customer base grows, so the identical deal prices as unprofitable today and profitable next quarter — useless in a quote. Contribution = price − (vendor tooling + delivery labor), i.e. only what scales with the deal; the fixed pool is handled once as `breakevenEndpointsAtThisTier`. Company-level absorption belongs on the CFO dashboard.
- **Hours per endpoint per month, by tier — measured, and it scales:** Standard **0.239**, Comprehensive **0.442**, Complete **0.697** (Complete ≈ 3× Standard). Basic and TCT Ally have **no live customers**, so they proxy Standard and Comprehensive respectively and are flagged `hoursAreProxied` — replace them the moment a real customer lands on either. Derived from 2,734 Autotask time entries (2026-02-01..2026-07-27) ÷ Datto RMM per-company endpoint counts, grouped by contract tier. **Endpoints = Windows PCs + servers**, because that is what Datto counts — counting workstations only would inflate hours/endpoint.
- **Blended delivery cost is $13.60/hr and deliberately EXCLUDES the advisory retainer.** Owner-confirmed 2026-07-28: that engagement is management/guidance, not a billable resource. It logged ~4.7 hrs/month against a ~$4k/month fixed fee, so treating it as delivery capacity would put the blended rate near $43/hr and triple every tier's labor cost. It sits in the fixed pool instead. A third contractor in the historical data left before derivation and is excluded from both cost and capacity.
- **Capacity is the real constraint, not cost.** Scalable delivery capacity is the two offshore contractors only (246.7 h/mo); ~224 h/mo is already logged, leaving **~22.6 h/mo idle**. A Wilmar-sized Complete Care deal needs ~96 h/mo, so it does NOT fit on idle time — `capacity.fitsInIdleCapacity` says so rather than quietly promising delivery. The growth runway is the **~109 h/mo currently spent on internal work** (48% of all logged time in the window). Check `fitsInIdleCapacity` before committing to a deal.
- **`labor.json` holds AGGREGATE figures only** — a blended rate and observed hours per endpoint. No individual pay rate and no named person, deliberately: this repo is public. Note `src/lib/cfo/hiring.ts` still carries named staff mapped to hourly rates (pre-existing, owner aware, decision deferred) — do not follow that pattern in new code.
- **Comparison exports**: `exportComparisonPDF()` (exporters.ts) produces landscape internal (costs/margins/internal product names, INTERNAL-USE footer) and customer (external names, prices only) versions from the Comparison card buttons. Matrix cells use words (`Included` / `T&M` / `Shared` / `—`), not icon glyphs — jsPDF's standard fonts don't cover them. The internal export button is hidden while the app is in customer view so costs can't leak on a screen share.

## MCP Connector Usage Telemetry — `/admin/connector/usage` (2026-07-28)

One row per MCP tool call in raw-pg **`connector_tool_calls`**, written by `src/lib/connector/telemetry.ts`, read by `/api/admin/connector/usage` and rendered at `/admin/connector/usage`. Built because `connector_staged_writes` only ever recorded *config* changes: there was no way to see who uses the connector, what fails, what it refuses to do, or which tools are context-expensive.

- **NEVER log tool arguments, response bodies, or error MESSAGES.** Arguments carry Autotask ticket contents, employee names and client data; vendor error strings quote ticket subjects and file names. The schema is the enforcement — `TELEMETRY_COLUMNS` in `telemetry.ts` is the complete column list, the INSERT is generated from it, and there is no free-text column that could hold a payload. Only names, classifications, outcomes, timings and response **size** are stored. `telemetry.test.ts` pins the column list and runs a hostile tool (one that echoes its own arguments into its response) to prove neither ends up in the row. Do not add an "error message" or "args" column for debuggability — Vercel function logs are the place for that.
- **The hook is `recordingServer()` in `capability-registry.ts`, nowhere else.** That proxy already intercepted every `registerTool` call for the capability report; it now also wraps each tool HANDLER. One hook for 126 tools; a tool added tomorrow is measured for free. Never add per-tool logging calls — that drifts on the 127th tool. Classification (vendor/access/risk/staged) comes from the existing `TOOL_FACTS`, never a second table.
- **Refusals are NOT failures.** A refusal is a call the connector deliberately declined: the staged-write gate (`approval_required` — a *successful* `*_stage_config_write` is a gate response by construction), a kill switch off (`kill_switch`), or missing vendor credentials (`not_configured`). They are demand signal and are counted separately, ranked by tool, so unmet demand is visible. Refusal markers are matched ONLY against error-path text (plus the structural stage rule) — matching them against successful responses miscounts an IT Glue configuration list containing the phrase "not configured" as a refusal.
- **Failure buckets map from the shared `classifyError()`** in `resilience.ts` (auth / rate_limit / vendor_unavailable / bad_input / other). Do not write a second classifier.
- **Fire-and-forget, error-swallowing, same posture as `api-usage-tracker.ts`.** The connector runs on Vercel serverless with `maxDuration 60`; a telemetry insert must never fail, delay or alter a tool call. `recordToolCall()` returns void immediately and hands the promise to Vercel's request-context `waitUntil` when it exists (read via `Symbol.for('@vercel/request-context')` — no `@vercel/functions` dependency), falling back to plain fire-and-forget locally. A missing table logs **once per instance**, not per call.
- **New table = POST `/api/migrations/run` once after deploy.** Until then nothing is recorded and the dashboard shows an explicit "telemetry table not created yet" banner (42P01 is caught and reported, never a 500). Tool calls are unaffected either way.
- **No Anthropic dollars on this page, ever.** The connector makes zero Anthropic API calls, so it contributes nothing to that bill. Response size is a context-weight proxy labelled in BYTES — never converted to dollars, never presented as an exact token count. Real AI spend stays at `/admin/monitoring`, which the page links to.
- **Retention is not implemented.** The table grows one row per tool call with no pruning cron. At current volumes that is fine for a long time, but a future `/api/cron/*` prune (or a `called_at` partition) is the obvious follow-up before it matters.

## MCP Connector Failure-Reason Envelope + Autotask Capability Layer (2026-07-28)

Every Autotask connector failure now returns a structured envelope alongside the human-readable message: `{failure:{reasonCode, message, evidence, remediation, fixableBy}}`. Built because four completely different problems were indistinguishable from the error text — the vendor can't do it, the connector wasn't built to do it, a TCT guardrail blocked it, or the credential lacks rights — and they have four completely different fixes, so the owner kept chasing the wrong one.

- **The taxonomy is closed: `NOT_IMPLEMENTED` / `UPSTREAM_UNSUPPORTED` / `POLICY_BLOCKED` / `PERMISSION_DENIED` / `PRECONDITION_FAILED` / `INVALID_INPUT` / `TRANSIENT`.** Defined once in `src/lib/connector/failure-envelope.ts`, which is **vendor-neutral by design** — IT Glue, UniFi, Datto RMM and HR SharePoint retrofit onto the same helper. Do not add a code, and do not define a per-vendor variant.
- **`fixableBy` is DERIVED from `reasonCode`, never passed in.** A caller able to set it independently could emit "UPSTREAM_UNSUPPORTED, fixableBy: claude_code", which routes the owner to the wrong person — the exact failure this removes.
- **NEVER hardcode an Autotask vendor limitation.** `UPSTREAM_UNSUPPORTED` for Autotask is always derived from a live `entityInformation` lookup (`src/lib/connector/autotask-capability.ts`), cached 30 min (`CONNECTOR_AT_CAPABILITY_TTL_MINUTES`). Kaseya ships API changes; a stale hardcoded "Autotask can't do this" is the precise failure mode this feature exists to eliminate.
- **Cold cache + failed lookup returns `TRANSIENT`, never `UPSTREAM_UNSUPPORTED`.** "I could not ask" is not evidence of "the vendor cannot". Getting this backwards would let a 30-second Autotask outage mint a permanent false limitation claim. A *stale* cache entry is used with a `staleWarning` instead of failing.
- **Evidence is mandatory for `UPSTREAM_UNSUPPORTED` at the TYPE level** (`FailureInput` is a discriminated union). A runtime backstop downgrades an uncited claim to `TRANSIENT` rather than emitting it, because "we don't know" is recoverable and a wrong "the vendor can't" is not.
- **ENTITY capability beats FIELD flags.** `BillingCodes` reports `canCreate/canUpdate/canDelete` all false while most of its *fields* report `isReadOnly false` (name, unitPrice, useType…). Check the entity operation first or you will conclude a read-only entity is writable.
- **`isReadOnly true` does NOT always mean "never settable".** `ServiceBundleServices` has `canCreate true` with *all three* fields `isReadOnly true` — that is only coherent if it means "immutable once written". Fields in this state live in a separate `createOnlyFields` list on the area spec (accepted on create, refused on update with the live metadata as evidence), never merged into `allowedFields`. **Every consumer of the flag must honour this — `autotask_capability_check` did not, and told the owner a required-on-create field "cannot be written by anyone" (see "Autotask Services / Service Bundles" below). Any field verdict must consult `createOnlyFields` and answer per operation before it reports a vendor limitation.**
- **A refused field must say whose problem it is.** `FieldsNotAllowlistedError` carries the field names as data so `classifyRejectedFields()` can ask live metadata: read-only upstream → `INVALID_INPUT`; writable upstream but not allowlisted → `NOT_IMPLEMENTED` **naming the exact file and area to extend**. Never return a generic "unsupported field".
- **There are THREE routes by which a caller can set a field, and `allowedFields` is only one of them.** `changes` → `allowedFields`; `changes` on create only → `createOnlyFields`; **`parentId` → `parentIdField`/`parentIdFromField`**, which `executeStagedWrite` writes into the create payload and uses to build the child REST path. Nothing consulted the third route, so **four fields the connector has always written were reported as unsupported on three separate surfaces** — the drift report listed them as missing writable fields, `autotask_capability_check` answered "no connector write area exposes it yet", and `classifyRejectedFields` called them a connector gap with a remediation to go build an allowlist entry. Worst case was `ServiceBundleServices.serviceBundleID`: `isReadOnly true` upstream **and required on every bundle-membership create**, answered as "cannot be written by anyone / do not offer to change this field". **Anything deciding whether a field is settable MUST go through `fieldSupplyRoutes()` / `settableFields()` in `staged-writes-core.ts` — never read `allowedFields` directly.** The four affected fields: `holiday`→`holidaySetID`, `checklist_library_item`→`checklistLibraryID`, `udf_list_item`→`udfFieldId`, `service_bundle_member`→`serviceBundleID`.
- **Parent-id fields get the same read-only exemption as `createOnlyFields`, and the same "unknown to the API" scrutiny.** `routeExemptFromReadOnly()` encodes the split: flagging a parent link as a suspect allowlist entry because it is read-only upstream would report the design as a defect, but a *typo* in a `parentIdField` breaks every create in that area and must stay reportable.
- **The stage tool description names each area's `parentId` field** (`AREA_SUMMARY` in `mcp-config-write-tools.ts`). Listing only `allowedFields` left callers to guess, and guessing `changes` is rejected as not-allowlisted — a supported write that reads as a broken one.
- **`Services.markupRate` was a real latent bug.** The old `service_pricing` allowlist accepted it; live metadata reports `isReadOnly true` (it is computed from unitPrice/unitCost). Removed. `autotask_surface_drift_report` → `suspectAllowlistedFields` is the check that catches this class, and it caught a second instance in freshly-written code (`serviceID` on the membership area) during the same session. **Run it after touching any allowlist.**
- **`autotask_capability_check` is the pre-flight tool** — ask *before* attempting, instead of failing and guessing. Verdicts (`SUPPORTED_AND_IMPLEMENTED` / `SUPPORTED_NOT_IMPLEMENTED` / `UPSTREAM_UNSUPPORTED` / `POLICY_GATED` / `UNKNOWN`) map onto the same taxonomy.
- **The envelope note is appended to tool descriptions in ONE place** — `annotateDescription()` inside `recordingServer()`. Per-file notes would drift on the next tool added. It is gated on `ENVELOPE_TOOL_PREFIXES`, so a surface that has NOT been retrofitted never advertises an envelope it does not return.
- **A 5xx is NOT proof of an outage — parse the body (2026-07-29).** `classifyError()` called any upstream 500 a `server_error`, i.e. `TRANSIENT` / `fixableBy: retry` / "wait briefly and retry the same call". Autotask returns **500 with a `Data violation` body** for schema violations, so the envelope actively instructed a retry loop on a failure that could never succeed (reproduced live on the assignment defect above). Fix: a new `data_violation` category in `src/lib/resilience.ts`, matched on the BODY (`data violation`, `missing required field`, `required field is missing`, `must assign both`) and checked **before every status pattern**, `isTransient: false`; `classifyThrown()` maps it to `PRECONDITION_FAILED` and puts the **vendor's own sentence** in `remediation` via `extractVendorRule()` (field names intact — paraphrasing loses the only actionable part). Deliberately narrow: genuine 5xx outages stay `TRANSIENT`, and an ordinary 400 stays `INVALID_INPUT` for the caller to fix, so the pattern list must NOT be loosened to phrases like "is required". Telemetry buckets `data_violation` as `bad_input`, not `vendor_unavailable` — otherwise the usage dashboard blames an outage for our own malformed request. `withRetry()` also stops retrying these, everywhere in the app.
- **`PRECONDITION_FAILED` derives `fixableBy: tct_human`, and that is the table's choice, not the call site's.** A data violation is usually closed by a *tool schema* change (Claude Code), but `FIXABLE_BY` is a total function of the reason code on purpose, and re-pointing `PRECONDITION_FAILED` at `claude_code` would misroute staged-write drift (which genuinely needs a human to re-read state). The routing is therefore carried in the remediation text, which names the schema fix explicitly. If the owner wants machine-routing to Claude Code for this class, the change is to emit `NOT_IMPLEMENTED` for it — not to edit the table.
- **Success shapes are untouched.** Only the failure path gained the envelope, and the failure text still starts with the original `Error: <message>` line so anything reading the first line still works.

## Kaseya Quote Manager (Datto Commerce) — read-only surface (2026-07-29)

Client `src/lib/kaseya-quote-manager.ts`, tools `src/lib/mcp-kaseya-quote-manager-tools.ts`, contract `docs/vendor-api/kaseya-quote-manager/COVERAGE.md`.

- **The vendor API has NO write surface.** All 39 operations in the captured OpenAPI spec are GET — verified from the spec itself, not taken on trust from Kaseya's "read-only" statement. So there is no staged-write gate and no kill switch for this surface, and there should never be one. A test asserts the spec still contains zero writes, so a future vendor POST fails the build and forces the read-only claim to be re-examined rather than silently invalidated.
- **PAGING IS 1-INDEXED** (spec default `page: 1`). This is the **opposite of Datto RMM**, whose 0-indexed paging silently skipped the first 250 rows of every sweep for months. Do not port a `page = 0` loop into this client. Locked by a test asserting the first request carries `page=1`.
- **No response carries a total count.** Every list endpoint returns a **bare JSON array** — no envelope, no `totalCount`. So a page-capped sweep is indistinguishable from a complete one unless it says so: `getAllPages()` returns `truncated`, the tools surface it, and a single-page read reports `likelyMorePages` instead of asserting a total it cannot know. Never compute or display an "X of Y" for this API.
- **The spec and Kaseya's help page appear to contradict each other on auth — SETTLED LIVE 2026-07-29: the API accepts the key BOTH ways.** The spec declares `securitySchemes.apiKey = {type: apiKey, name: "apiKey", in: "header"}`; the help page describes a QUERY PARAMETER (and is itself inconsistent on casing). The probe returned 200 for **both**, so neither doc is wrong — each is incomplete. **Keep the header default for a security reason, not a doc-authority reason:** a key in a query parameter lands in the URL, and therefore in access logs, proxy logs and any error report that echoes the request line. Do not set `KASEYA_QUOTE_MANAGER_AUTH_MODE=query` without a specific reason.
- **The probe tries each mechanism IN ISOLATION — never both at once.** Sending the key as a header *and* a query parameter would make a 200 uninterpretable: you would know it authenticated but not which channel the API read. Do not "helpfully" send both.
- **The probe's own first version overstated its evidence — fixed same day.** It reported `working` as the FIRST mechanism that succeeded and then claimed the help page "can be disregarded". When both mechanisms work, that is a confident claim the observation never supported, produced by the very diagnostic built to stop confident-but-unsupported vendor claims. It now returns **`accepted`** (every mechanism that authenticated) alongside `working` (the one the client will actually use, which prefers the configured mode over probe order), with a four-way recommendation — none / both / only-default / only-other. Locked by one test per outcome, including an assertion that the wording never again says a vendor doc "can be disregarded". Lesson, third time this week: **a diagnostic that collapses two observations into one answer is indistinguishable from a diagnostic that guessed.**
- **Only the spec's own query parameters are exposed as filters.** The API **ignores unknown query parameters rather than erroring**, so advertising a filter it does not implement would return the full set while looking filtered — wrong results that read as correct. A test asserts no undocumented parameter is exposed. Notably: products filter by `manufacturerPartNumber` **exact match only** (no name search), quotes by `quoteNumber` only (no customer or date-range filter), and `quoteline` filters by `quoteSectionID` — **not** by quote id, so resolve sections via `kqm_quote_sections` first.
- **`modifiedAfter` exists on only 15 of the 20 resources** — absent on `category`, `employee`, `productimage`, `quoteline`, `quotesection`. A delta sync is not available for those, and the tools must not advertise it there.
- **`productimage` has no get-by-id** — it is the only such resource (20 lists + 19 by-id = 39). Advertising an `id` for it would 404 indistinguishably from a missing record.
- **`category` has no paging and no filters at all** — the only resource where the API returns the full set in one response.
- **Rate limits are NOT in the spec** — 60/min, 20,000/24h and HTTP 429 come from the help page only. Enforced two ways deliberately: a per-instance sliding window *and* reactive 429 retry through `withRetry`. The window is per-lambda, so across concurrent Vercel instances it is a floor, not a guarantee; neither layer is sufficient alone.
- **`pageSize` is clamped to 100.** The help page states that cap; the spec states 100 only as a *default* and gives no maximum. Passing a larger value would be a silent gamble on undocumented behaviour.
- **`kqm_` adopted the failure envelope from its first commit** rather than being retrofitted — the taxonomy in `failure-envelope.ts` is vendor-neutral for exactly this reason, and a brand-new surface has no plain-text callers to break.
- **Live-verified 2026-07-29** against production: the key authenticates, both auth mechanisms work, `pageSizeCapHonoured: true`, and `/v1/warehouse` returned the bare array the spec declares. **Still unverified:** real 429 behaviour (not deliberately provoked) and response-shape drift on the other 19 resources — observations to make in normal use, not blockers.

## Autotask Services / Service Bundles — write surface (2026-07-28)

Live `entityInformation` (2026-07-28), and the reason each area looks the way it does:

- **`Services`**: canQuery/canCreate/canUpdate **true**, canDelete **FALSE** → deactivate with `isActive:false`; delete is derived-absent, not a choice. Read-only: `id`, `createDate`, `lastModifiedDate`, `creatorResourceID`, `updateResourceID`, `markupRate`, `periodType`.
- **`ServiceBundles`**: canDelete **true** (unlike Services — do not generalise from one to the other). `unitCost` is read-only: it rolls up from member services.
- **`ServiceBundleServices`** (membership): canCreate **true**, canDelete **true**, canUpdate **FALSE** → membership is add/remove only; change a bundle by deleting a row and creating a new one.
- **`periodType` is flagged `isRequired` AND `isReadOnly` at once on both entities** — contradictory, and the flags alone cannot say whether it is settable at create and merely immutable after. It is exposed as `createOnlyFields`. **SETTLED EMPIRICALLY 2026-07-28: it IS settable on create, and it is MANDATORY there.** Service ids 131–136 (the TCT Ally catalog) were created through the connector with `periodType: 2` and read back as `{id: 2, label: 'Monthly'}`; the one staged create that omitted it failed on Autotask's own `500 "Missing Required Field: periodType"` — *after* spending a human approval. So `periodType` is now in `requiredOnCreate` for `service` and `service_bundle`: a create that omits it is rejected at stage time with a precise message instead of burning an approval round trip. (The `ServiceBundles` half is metadata-derived, not yet exercised by a real bundle create — the flag proved accurate for `Services`, and requiring a legitimate create value costs a caller nothing.)
- **A create-only field must never be reported as a vendor limitation — this shipped broken and was caught in production.** `autotask_capability_check` answered `verdict: UPSTREAM_UNSUPPORTED`, "`Services.periodType` is read-only in the Autotask API, so it cannot be written by anyone", remediation "Do not offer to change this field" — for a field that is **required** on create. A caller obeying that omits `periodType` and *every* Service create fails. The cause: the `isReadOnly` branch in `checkAutotaskCapability()` returned before consulting `createOnlyFields`, even though the surrounding code had already computed it (`allowlistedIn` includes create-only fields, which is why the same response said `implemented: true`). The connector knew and threw the fact away. **The field verdict is now operation-aware**: `create` → `permits: true` + `POLICY_GATED`; `update`/`delete` → `UPSTREAM_UNSUPPORTED` worded as *immutable after create, not unwritable*; operation unspecified → `permits: null` with the split spelled out in the evidence. Pass `operation` alongside `field` whenever you know it. Lesson: the failure-envelope layer exists to stop false "the vendor can't" claims, so a false claim **produced by that layer itself** is the worst version of the bug — a read-only flag is a question, not a verdict.
- **`suspectAllowlistedFields` skipped create-only fields entirely**, so a typo in a `createOnlyFields` entry was unreportable by the drift report. Only the *read-only* half of that check is inapplicable to create-only fields; "unknown to the API" always applies, because sending a non-existent field on create fails just the same. Fixed and regression-locked.
- **`ServiceBundleServices.serviceBundleID` reproduced the periodType bug on a THIRD route (2026-07-29), found by running the drift report.** It is `isReadOnly true` upstream, **required** for every bundle-membership create, and written into the create payload on every one — yet `autotask_capability_check` answered "cannot be written by anyone / do not offer to change this field", because the fix above taught the `isReadOnly` branch to consult `createOnlyFields` but not `parentIdField`. Membership adds would have been reported impossible right when the `service_bundle` create path went live. Now routed through `fieldSupplyRoutes()` so all three supply routes are consulted at once, and locked by tests naming the exact wording that was wrong. **Lesson, second time: when a false vendor claim is traced to one unconsulted source of truth, enumerate the others in the same commit — the bug is "the code knew and threw it away", and it recurs on whichever route was not enumerated.**
- **Validation happens at STAGE time, not execute time**: `billingCodeID` must be an active code with `useType 5` (= "Recurring Contract Service Code", confirmed live), `serviceLevelAgreementID` must be a live picklist value (1 Standard / 2 TCT Fully Managed / 3 No SLA), and same-name/SKU duplicates are surfaced as **warnings in the diff** (not blocks — the catalog has real intentional near-duplicates, and the human approving is better placed to judge). A staged row that cannot execute wastes the approver's attention.
- **`service_pricing` is retired but still callable**, aliased to the `service` area via `CONFIG_AREA_ALIASES` so older prompts keep working. One implementation, resolved before validation — do not create a second Services write path.

## Delivery Economics report — `/admin/reporting/delivery-economics` (2026-07-28)

Cost-to-serve, capacity and billing capture, measured from Autotask time entries joined to Datto RMM endpoint counts. Engine: `src/lib/reporting/delivery-economics/` (pure `analyzer.ts` + I/O `service.ts` + raw-pg `snapshots.ts`). API `GET/POST /api/reports/delivery-economics` (staff session OR `MIGRATION_SECRET`), weekly cron `/api/cron/delivery-economics-snapshot` (Mondays 09:00 UTC). **New table `delivery_economics_snapshots` = POST `/api/migrations/run` once after deploy.**

- **Snapshots are APPEND-ONLY and that is the whole point.** A single reading of this report is nearly useless; the finding that mattered in the first derivation was a TREND — internal-work share fell from 66% (Feb 2026) to 25% (Jul 2026) while customer hours rose 40%. Never add an upsert or a prune that collapses history. Full report JSON is retained per row so a future question can be asked of past data without re-pulling Autotask.
- **Autotask TimeEntries pagination 405s on a full month.** A whole-month window reliably fails after 500 records with *"The requested resource does not support http method 'GET'"*. `buildFetchSlices()` fetches in HALF-MONTH slices and de-dupes by entry id. Do NOT "simplify" this back to one call per month — it will fail on any busy month. One failed slice degrades that slice only and is reported in `notes`, never silently treated as zero hours.
- **`companyID === 0` means INTERNAL work**, not null. Autotask uses 0. A `== null` check misses every internal entry and inflates customer-facing hours.
- **Endpoints = Datto RMM managed devices, which INCLUDE servers.** Hours-per-endpoint must be divided by the same population it was measured against. Datto site pagination is **0-indexed** (page 1 skips the first 250 rows), and the endpoint→Autotask-company mapping lives on the raw `autotaskCompanyId` field, which the typed client does not surface — hence `getV2()`.
- **A tier with no customers reports `null` hours-per-endpoint and `measured: false`, never 0.** A fabricated zero reads as "this tier is free to deliver". Basic Care and Ally have no live customers, so the sales calculator proxies them (see Sales Calculator → labor model).
- **Tier comes from the contract NAME, not the category.** "Managed Service - Gold" covers both Standard and Comprehensive contracts, and some managed contracts have no category at all. Internal codenames count: **Bastion = Comprehensive, Fortress = Complete**. When a company holds several managed contracts the RICHEST wins (`TIER_RANK`) — a Complete Care customer who also has a Gold-category "Microsoft Licenses" contract is a Complete Care customer.
- **Billing capture reads `billingStatus` (from BillingItems), not the `billable` boolean.** The boolean records intent at entry time; only BillingItems knows what was invoiced. Live June 2026: Standard 37% invoiced, Comprehensive 31%, Complete 42% — and only 4.33 h company-wide sat `unposted`, so write-offs are a decision made at entry, not an invoicing backlog.
- **Non-billable is NOT all recoverable revenue — split it before quoting a number.** Standard Care's written-off time is overwhelmingly sub-30-minute proactive monitoring and alert response (backup failures, SMART alerts, malware detections) plus a proactive-notification campaign. That is work TCT initiated and is correctly unbilled — on non-Complete tiers the policy is to inform the customer and quote the fix, so the notification itself is never billable. The recoverable end is **project-sized entries (2 h+)**: 6 entries / 20.70 h in the first window, one on-site project alone 17.65 h. Lumping the two together overstates recoverable revenue by roughly 10× (an early pass said $55k/yr; the honest figure was $6–11k/yr).
- **`classifyWorkNature()` checks proactive-notification FIRST** — the outreach template contains the words "security" and "Windows machines", so any other ordering files a notification campaign as incident work.

### Cost to serve is measured per BILLED UNIT, not per endpoint (2026-07-29)

The first version of this report normalised everything per Datto endpoint. **TCT does not bill per endpoint.** A recurring invoice is a set of independent lines, each with its own unit type and quantity — verified against two live Complete Care invoices:

| | Tri-Bros (398) INV100424 | EZ Red (420) INV100439 |
|---|---|---|
| Per company (`TCT Complete Business`) | 1 × $250.00 | 1 × $500.00 |
| Per user (`TCT-Complete-User`) | 15 × $100.00 | 32 × $33.60 |
| Per device (`TCT-Complete-Device`) | 20 × $50.00 | 28 × $60.00 |
| Managed MRR | $2,750.00 | $3,255.20 |
| Billed through (licences / backup / add-ons) | $45.00 | $848.80 |

Engine: `billing-units.ts` (pure). Locked by `billing-units.test.ts`, which reconstructs both invoices to the cent — EZ Red's total lands exactly on its $4,104.00 Total Billable Amount, Tri-Bros's on $2,845.00 less the $50.00 of mid-month prorations. **If those assertions fail, fix the model, not the expected totals.**

- **Users and devices are independent counts and the ratio INVERTS between customers** (15 users/20 devices vs 32/28). A single endpoint denominator assumes they move together, so per-user services — a third to a half of managed revenue — had no cost basis at all.
- **Rates come from the CONTRACT, never the service catalogue.** The catalogue is a default that live contracts routinely override: `TCT-Complete-User` lists at $80 while one customer pays $100 and another $33.60. Reading catalogue rates would misstate revenue on nearly every managed customer. `rateSource` records the provenance; `computeRateVariance()` reports the gap as a **discount ledger**, not a defect list (older contracts were signed against older list prices).
- **`ContractServiceUnits` holds one row per service PER BILLING PERIOD — never sum it.** A three-year contract carries ~36 rows per service, so summing reports 36× the real headcount. `buildCompanyBilling({ anchorDate })` picks the period covering the anchor, falling back to the latest period that *started* before it (rows are written ahead by a scheduled job, and a contract can briefly have no current row — treating that as zero units erases the customer).
- **Autotask splits one invoice line across THREE entities** and there is no endpoint that returns it whole: `Services` has the name, `ContractServices` the rate (no quantity), `ContractServiceUnits` the quantity. `ContractServices` is creatable/updatable in the API but is read-only here by intent — pricing changes belong in the gated staged-write flow, never a reporting path.
- **Unit-type classification is by service NAME and the pattern order is load-bearing.** Traps, all real catalogue entries: `Microsoft 365 **Business** Premium` is a resold licence, not the per-company line (licences must match first); `TCT-Complete-User-**SharedMailbox**` is a per-mailbox add-on, not a user seat; `Email Protection - Business` and `Business Password Manager` are add-ons. **`Remote PC Access` matched `/\bpc\b/` and was counted as a managed device** — on a real invoice that turned 20 devices into 21 and shifted every per-device figure. Unmatched names return `'other'` and are surfaced in `unclassifiedServices` rather than absorbed into the wrong bucket.
- **The labour fit gates on ADJUSTED R², never raw R².** Hours are logged per customer, not per unit type, so the user/device split is fitted (OLS on users + devices + servers + intercept, negative coefficients dropped then clamped at zero). With ~10–25 customers and 3–4 parameters raw R² flatters noise badly: hours generated to be *independent* of customer size still score 0.48–0.62, while adjusted R² puts them at 0.22. Below the threshold it falls back to an even per-unit allocation and reports `method: 'unit-share'` — **that value is part of the finding, not metadata.** Presenting an allocation as a measurement is the same class of error as the per-endpoint model this replaced.
- **The fallback allocation is deliberately FLAT, not revenue-weighted.** Weighting labour by price would make the expensive line look expensive to deliver purely because it is priced higher — it launders the pricing assumption back in as if it were a measurement, and testing that assumption is the entire purpose of the report.
- **Contribution, never absorption**, unchanged from the calculator's labour layer: the fixed pool is reported separately rather than spread over units. The fit's fixed per-company hours are charged to the **business** line once per company (not per business unit), so a business line can show a loss while the customer overall is profitable.
- **Endpoint figures are kept but relabelled "RMM coverage".** Endpoints under management are not the same population as billed device units, and the tier proxies in `labor.json` were derived from them.
- **ContractServiceUnits MUST be queried PER CONTRACT with a date window — the 405 gotcha bites hard here (2026-07-29, live).** The first production run returned `$0` managed revenue and an empty billed-unit section. Cause: `listContractServiceUnits()` was an account-wide `queryAll` with `includeFields`, and unit rows are one per service **per billing period** — a single three-year contract contributes ~36 rows per service, so the query blew past the 500-record first page and this zone 405s on the `nextPageUrl` GET for `includeFields` queries. Now fetched per contract over a ~6-week window (`CONTRACT_FETCH_CONCURRENCY`, `UNIT_WINDOW_LOOKBACK_DAYS`) so every response fits one page and `nextPageUrl` is never followed. Locked by a test asserting every unit query carries BOTH a `contractId` and a window. Do not "simplify" it back to one call.
