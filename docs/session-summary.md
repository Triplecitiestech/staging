## HR Employee Relations: `hr_er_log_update` (2026-07-31) — branch `claude/hr-er-log-update-tool-c83fn8`

A structural gap, not a nice-to-have. `hr_er_log_append`'s own `meetingWithTech` description tells the caller to leave the field unset until the conversation with the technician has happened — so it is *guaranteed* to need filling afterwards. Same for `followUpStatus` when an item closes and `linkedDocument` when a write-up is filed later. Live case: **ER-0005**, appended 2026-07-31 with "Meeting with Tech" and "Linked Document" blank. The conversation has since happened, and the text has to land in that row — a second row would inflate the subject's disciplinary record.

**What it does.** `hr_er_log_update` takes `entryId` plus at least one of the 13 patchable fields (identical names/types/descriptions to `hr_er_log_append`, so the two are interchangeable in a caller's head), locates the single matching row, and patches only the named columns. `appendToSummary` / `appendToMeetingWithTech` (default false) add the new text on a new line instead of replacing, because follow-up conversations accumulate.

**The refusals matter more than the writes.**

- Unknown Entry ID → `PRECONDITION_FAILED` listing the ids that DO exist, pointing at `hr_er_log_columns`. It never falls back to appending.
- Same Entry ID on two rows → `PRECONDITION_FAILED` naming both row indices and their sheet rows. No tiebreak exists that isn't a guess.
- A named column that is not in the live header row → `PRECONDITION_FAILED`, and **nothing is written at all**, not even the columns that were resolvable. (Append only warns in the equivalent case — it padded a column that lost nothing; update was explicitly told to write that cell.)
- No patch fields → `INVALID_INPUT` before any Graph call.

**Three decisions worth remembering.**

1. **Single-cell PATCHes, never a row PATCH.** Graph's `tables/{name}/rows/itemAt(index=N)` takes the whole row's values — that would replace any formula in the row with a computed value and touch cells nobody named. So: `/dataBodyRange?$select=address,values` for the absolute address, then one `PATCH /worksheets/{sheet}/range(address='<cell>')` per changed column. "Only the named columns" has to mean the others are not written at all.
2. **Entry ID and Date Logged are unwritable by construction**, not by a runtime check: `ER_UPDATABLE_FIELDS = ER_FIELDS.filter(kind !== 'computed')`, and a test pins the schema key set to exactly `entryId` + those fields + the two flags. Date Logged records when the entry was *created*.
3. **Verification is never claimed without proof.** The Entry ID cell is re-read at its exact address before writing (refuse if the row moved) and the row is re-located *by Entry ID* on read-back. A `YYYY-MM-DD` expectation also matches a numeric cell whose Excel serial converts to that date — a date-formatted column returns a serial, and without that equivalence every date patch would report `verified: false` and train the reader to ignore the flag.

**Verification.** 66 new tests (37 pure + 29 end-to-end through the registered tool handler against an in-memory workbook that applies the PATCHes, so a write to the neighbouring row fails the test). Full suite 800 passed, lint clean, `next build` compiles. The three existing HR tools and their shared helpers were confirmed **byte-identical to HEAD**; the only pre-existing lines touched are the `auditHrWrite` operation union and one `hr_er_log_columns` constraint string.

## Kaseya Quote Manager: live verification + probe fix (2026-07-29e) — branch `claude/kqm-probe-both-auth-modes`

First real calls to the Kaseya API, and a fix to the diagnostic that made them.

**Verified live** (production, commit `d8f9992bc179`): the key authenticates, `pageSizeCapHonoured: true`, and `/v1/warehouse` returned the bare JSON array the spec declares. All 21 `kqm_*` tools are in the deployed registry, classified `access: read` with no staged approval.

**The auth question resolved to an answer none of my three branches covered: the API accepts the key BOTH ways.** Header → 200. Query parameter → 200. So neither Kaseya doc is wrong; each documents one mechanism and omits the other. We keep the header — but the reason changed from "the spec is more authoritative" to a **security** one: a key sent as a query parameter ends up in the URL, and therefore in access logs, proxy logs, and any error report that echoes the request line. That is a better reason than doc precedence, and it is now the one recorded.

**The probe itself was defective, in this session's recurring pattern.** `working` was `results.find(r => r.ok)?.mode` — the FIRST success — and because `header` is probed first, the both-work case reported header and then asserted "the help page's contradictory description can be disregarded". That is a confident claim the observation never supported, emitted by the very tool built to stop confident-but-unsupported vendor claims. Same shape as the `periodType` and `parentIdField` bugs earlier in the week: the code had the evidence and threw half of it away.

- Now returns **`accepted`** — every mechanism that authenticated — alongside `working`, which is the mode the client will actually use and **prefers the configured mode over probe order** (so it describes behaviour, not iteration sequence).
- Recommendation became a four-case function: none / both / only-default / only-other. The both case explains the log-hygiene reason to keep the header; the only-other case flags the URL-leak tradeoff rather than presenting a switch as free.
- Locked by one test per outcome, including `expect(recommendation).not.toMatch(/can be disregarded/)` — the exact wording that was wrong.

**Verification.** 24 KQM tests (6 new), full suite green, lint clean, build compiles.

## Kaseya Quote Manager connector tools (2026-07-29d) — branch `claude/tct-mcp-failure-reasons-ew5tz0`

Step 2 of 2. Step 1 (`8b2f720`) captured the spec and stopped for review; this builds the surface. **No migration** — no schema changes.

**Read-only twice over.** `src/lib/kaseya-quote-manager.ts` exposes `get()` as its only network path — there is no method or body parameter anywhere in its public surface to override — *and* the vendor API has no write surface at all: all 39 operations in the captured spec are GET. That second fact is verified from the spec rather than trusted from Kaseya's statement, and a test asserts it still holds, so a future vendor POST fails the build instead of silently invalidating every "read-only" claim in the tool descriptions. There is deliberately no staged-write gate and no kill switch for this surface.

**Coverage is a test, not a promise.** 20 tools cover 39 operations (each resource handles both list and get-by-id). The surface is generated from one table, `KQM_RESOURCES`, which `mcp-kaseya-quote-manager-tools.test.ts` asserts against `openapi.json`: every spec GET reachable, every documented query parameter exposed, `modifiedAfter` on exactly the 15 supporting resources, and `productimage` — the only resource with no get-by-id — not advertising one. 20 hand-copied tool blocks would have drifted from the spec on the first vendor change.

- **The inverse assertion is the valuable one:** no *undocumented* parameter may be exposed. The API **ignores unknown query parameters rather than erroring**, so advertising a filter it does not implement would return the full set while looking filtered — wrong results that read as correct. That is a silent-failure mode, so it is locked by test.
- **Paging is 1-INDEXED** (spec default 1) — the opposite of Datto RMM, whose 0-indexed paging silently skipped the first 250 rows of every sweep for months. A test asserts the first request carries `page=1`.
- **No response carries a total count.** Every list endpoint returns a bare array. So a capped sweep reports `truncated: true` with a note, and a single-page read reports `likelyMorePages` rather than asserting a total the API cannot provide. Without that flag a page-capped sweep is indistinguishable from a complete one.
- **`kqm_` adopted the failure envelope from its first commit** rather than being retrofitted — the taxonomy is vendor-neutral for exactly this, and a new surface has no plain-text callers to break. `ENVELOPE_TOOL_PREFIXES` gained `kqm_`.
- **TOOL_FACTS entries are written one per line, not generated** from `KQM_RESOURCES`. Deriving them from the same table that registers the tools would mean a newly added resource mints its own "reviewed" facts entry with nobody reviewing it — precisely the drift the completeness test exists to catch. Constraints name the real per-resource limits (products are MPN-exact-match only; quote lines filter by section id, not quote id).

**The auth contradiction, unresolved by the vendor.** The spec declares `securitySchemes.apiKey = {type: apiKey, name: "apiKey", in: "header"}`; Kaseya's help page describes a query parameter and is itself inconsistent on casing. These disagree on the *mechanism*. The header is the default — a generated spec beats hand-written prose — and `kqm_probe_connection` settles it against the live API, trying each mechanism **in isolation** because a key sent both ways makes a 200 uninterpretable. `KASEYA_QUOTE_MANAGER_AUTH_MODE=query` applies the other answer with no code change. Rate limits (60/min, 20k/day) are help-page-only and enforced both proactively per-instance and reactively via `withRetry`; the per-lambda window is a floor, not a guarantee.

**Verification.** 583/583 unit tests across 37 files (18 new), `next lint` clean, `next build` compiles, `tsc --noEmit` clean apart from the pre-existing `mcp-datto-rmm-tools.test.ts` `proxySettings` error. **No live call has been made and nothing about real API behaviour is confirmed** — auth mechanism, real 429 handling, the `pageSize` cap and response-shape drift are all unverified until `kqm_probe_connection` runs against the deployed app. The owner created `KASEYA_QUOTE_MANAGER_API_KEY` in Vercel on 2026-07-29 but had not redeployed; this deploy is what exposes it, since a variable added after a deployment is not visible to it.

## Three connector defects: IT Glue moves, Autotask assignment, retry advice (2026-07-29c) — branch `claude/tct-mcp-connector-fixes-lb7e5k`

All three reported by the owner from a live session against IT Glue org 6942365 and production Autotask. Two of the three shared one root cause in behaviour, not in code: **a tool returned success-shaped output on failure**, so the caller could not tell "the vendor refused" from "the connector is broken" from "it worked".

**1 — IT Glue folder moves are not possible, at all (twelve days undetected).** `document_folder_id` is CREATE-ONLY: IT Glue's developer reference marks it *"Not permitted in PUT/PATCH, optional in POST"* on `PATCH /documents/:id` and on the bulk `PATCH /documents`, while documenting it on `POST /documents`. IT Glue does not error on the rejected attribute — it drops it and answers **200 with the document unchanged**. So `itglue_move_document` reported `moved:false` with no error (doc 24262329 → folder 5301326 on 07-17, doc 24227609 → folder 6255494 on 07-29), and `itglue_rename_document` accepted `documentFolderId` and silently ignored it.

- `itglue_move_document` now **issues no write** and returns `UPSTREAM_UNSUPPORTED` / `fixableBy: vendor`, quoting the vendor's own wording as evidence and reporting the document's CURRENT folder so the user can be told where it actually is (and told plainly if it is already in the target folder).
- `itglue_rename_document` **refuses the whole call before renaming** when `documentFolderId` is supplied — fail-closed beats a half-applied write — and verifies the new title by read-back.
- `ItGlueClient.updateDocument` types `documentFolderId` as `never` and throws if one arrives through a cast, so no future call site can resurrect the silent no-op. Evidence lives in one exported constant (`DOCUMENT_FOLDER_MOVE_UNSUPPORTED`) cited by the tools and `known-limits.ts`.
- **The two things that DO work**: pass `documentFolderId` at create time, or have a human move it in the IT Glue UI (Documents list → tick → Move). `itglue_create_document`'s description now says create is the only chance to set it.

**2 — Autotask assignment failed 100% of the time.** Any Tickets write setting `assignedResourceID` without `assignedResourceRoleID` returns `500 Data violation: When assigning a Resource, you must assign both a assignedResourceID and assignedResourceRoleID.` Both tools now accept the role, and the pairing is enforced in the **writer** (`applyAssignedResourceRole()` inside `createTicket` AND `updateTicket`) rather than in the tools, so no future caller can reintroduce a lone resource id. Default **Engineer 29683355**; Help Desk 29683464 and Network Engineer 29683460 are the other valid roles; Low/High Voltage Technician 29683465 is never a default. Clearing an assignment (`null`) deliberately does not acquire a role. Both writes are **verified by read-back** via a new narrow `getTicketAssignment()` query — deliberately not a widening of the shared `TICKET_QUERY_FIELDS`, which the reporting sync also uses: an accepted PATCH that did not stick returns `PRECONDITION_FAILED`, and a create whose assignment did not take returns the ticket with `assignmentVerified: false`.

**3 — A 5xx is not proof of an outage.** `classifyError()` treated every upstream 500 as `server_error` → `TRANSIENT` / `fixableBy: retry` / "wait briefly and retry the same call". Autotask answers schema violations with 500, so the envelope actively instructed a retry loop on a failure that could never succeed. New `data_violation` category in `resilience.ts`, matched on the **body** and checked before every status pattern, `isTransient: false` — which also stops `withRetry()` retrying these anywhere in the app. `classifyThrown()` maps it to `PRECONDITION_FAILED` and puts the **vendor's own sentence** in `remediation` (`extractVendorRule()`, field names intact). Kept deliberately narrow: genuine 5xx outages stay `TRANSIENT` and an ordinary 400 stays `INVALID_INPUT`, both locked by tests.

**One thing the owner asked for that could not be honoured literally.** He asked for `NOT_IMPLEMENTED` + `fixableBy: vendor` on the IT Glue defect and `PRECONDITION_FAILED` + `fixableBy: "developer"` on the classifier. `fixableBy` is a **derived total function** of `reasonCode` by design, so neither pair exists: `fixableBy: vendor` IS `UPSTREAM_UNSUPPORTED` (used, with the mandatory evidence), and `PRECONDITION_FAILED` derives `tct_human`. Re-pointing `PRECONDITION_FAILED` at `claude_code` would misroute staged-write drift, which genuinely needs a human to re-read state — so the developer routing is carried explicitly in the remediation text instead. If machine-routing matters more than the code's meaning here, the change is to emit `NOT_IMPLEMENTED` for data violations, one line.

## Drift report run + the parent-id false-report fix (2026-07-29b) — branch `claude/tct-mcp-failure-reasons-ew5tz0`

Follow-up to the section below. The checklist's step 2 was "run `autotask_surface_drift_report` once and read it" — the payoff tool. Running it produced a clean bill of health on the thing it was built to check (**0 suspect allowlisted fields across 44 entities, 0 lookup failures** — no allowlist is currently claiming a field Autotask would reject) and, reading the output critically, exposed a defect in the report itself.

**The bug: a caller can set a field by three routes, and only two were ever consulted.**

| Route | Spec field | Passed as |
|---|---|---|
| `changes` | `allowedFields` | `changes` |
| `changes`, create only | `createOnlyFields` | `changes` |
| **parent id** | **`parentIdField` / `parentIdFromField`** | **`parentId`** |

The third is how child entities work: `executeStagedWrite` builds the child REST path from it *and* writes it into the create payload (`staged-writes.ts:410`). Prompted by a review of the open-source `tegwin/AutotaskMCP` server vs our integration (verdict: ours is more mature; two of its ideas were worth adopting). Changes:
- **`queryAll` accepts `includeFields`** and ticket queries (`getCompanyTickets`, `getTicket`, `getTicketByNumber`) now request only `TICKET_QUERY_FIELDS` (the `AutotaskTicket` interface fields) — without it Autotask returns ~80 fields + userDefinedFields per ticket on every reporting-sync pull.
- **Wired `resilience.ts` into the client**: GET/query/PATCH go through `withRetry` (2 retries, 1s base, transient-only — 429/5xx/timeout). POST deliberately not retried (non-idempotent creates would duplicate notes/time entries). Permanent 4xx surfaces immediately so entity-path fallback chains stay fast.
- **Pagination no longer silently truncates**: a page that fails after retries now throws (`Autotask pagination for X failed after N records`) instead of returning a partial set — this was the root cause of the "empty phases" gotcha. Callers (per-company ticket sync, fallback chains) already handle thrown errors at the right granularity.
- New unit tests `src/lib/autotask.test.ts` (mocked fetch: includeFields body, 429 retry, 404 no-retry, multi-page concat, truncation throw, PATCH retry, POST no-retry). Removed a stale "extended ticket fetch" comment in `reporting/sync.ts`. Gotchas updated (Autotask section).

## Customer-portal approval loop (closed end-to-end)

1. Operator clicks "Request customer approval" on a policy row
2. Server creates `compliance_policy_approvals` row + HMAC-signed magic link + Resend email
3. Customer clicks link → `/portal/policy-approval/[token]` (token-gated, no login)
4. Customer reads policy, approves or rejects with notes
5. Status surfaces back as a badge on the operator's policy row + a "Waiting on customer" panel on the workflow landing
6. When operator hits Publish: the executor checks the approval table as the AUTHORITATIVE gate. Operator-vouching checkbox is the fallback path only.
